## 第 1 章 分布式系统的特征

### 知识点组 1｜构建原因、定义与基本特征

【配套：《知识点整理》§1.1–1.4】

**选择｜** 分布式系统的三个基本特点是：
A. 并发性、无全局时钟、故障独立性  B. 透明性、并发性、安全性  C. 异构性、开放性、可伸缩性
**答案：A**（透明性等是"挑战"，不是"特点"——注意区分两套清单）。

**判断｜** 分布式系统协调动作的唯一途径是消息传递。
**答案：对**——CDK 定义的原文要素：网络计算机上的组件仅通过传递消息通信与协调。

**判断｜** "一些进程出现故障，其他进程必定都能知道"是分布式系统的基本特点之一。
**答案：错**——特点是**故障独立性**：不能保证其他进程知道。

**简答｜** 简述为什么需要分布式系统（构建原因）及其目标。
**答案要点**：功能分离、固有分布性、负载均衡、可靠性、经济性；目标 = 资源共享 + 协同计算。

### 知识点组 2｜七大挑战与 RPC

【配套：《知识点整理》§1.5–1.6】

**选择｜** "用户使用 URL 访问资源，无需知道其在源服务器、代理还是 CDN"属于：
A. 访问透明  B. 位置透明  C. 复制透明
**答案：B**。

**选择｜** 中间件的作用是：A. 提高带宽  B. 屏蔽底层异构性  C. 检测进程故障
**答案：B**——异构性的对策即中间件与移动代码/虚拟机。

**简答｜** 列举分布式系统面临的挑战（至少 5 个）并各举一例。
**答案要点**：异构性（中间件）、开放性（公开 API）、安全性（机密/完整/可用）、可伸缩性（DNS 分区缓存复制）、故障处理（检测/屏蔽/容错/恢复/冗余）、并发、透明性（8 种：访问/位置/并发/复制/故障/移动/性能/扩展）。

**简答｜** 描述一次 RPC 的完整信息流；为什么需要 stub 与序列化？
**答案要点**：client 调 stub → 打包参数（marshalling）→ 网络消息 → server stub 解包 → 调本地函数 → 结果反向；stub 由 IDL 生成；序列化解决语言/宽度/字节序差异，指针无意义。

## 第 2 章 系统模型

### 知识点组 3｜体系结构模型（C/S、P2P、分层、放置）

【配套：《知识点整理》§2.1–2.2】

**选择｜** 直接通信范型（IPC、远程调用）的两个限制是：
**答案：空间耦合**（发送者须知道接收者）与**时间耦合**（双方须同时存在）——间接通信（组通信、发布订阅、消息队列、DSM、元组空间）正是为解耦二者。

**判断｜** C/S 结构的伸缩性不会超过服务器的能力与其网络带宽。
**答案：对**——这是 C/S 的固有缺陷；P2P 的服务能力随用户数增长。

**简答｜** 区分分层体系结构与层次化（tiered）体系结构。
**答案要点**：分层=按技术栈垂直组织（平台/中间件/应用），每层用下层服务；层次化=从应用角度组织功能（如 web 三层），是"组织给定层功能"的技术，与分层互补。

### 知识点组 4｜基础模型：交互/故障/安全，同步与异步系统

【配套：《知识点整理》§2.3–2.5】

**选择｜** 只可能发生在同步分布式系统中的故障是：A. 遗漏  B. 拜占庭  C. 时序
**答案：C**——异步系统无时间保证，谈不上"时序"故障。

**判断｜** 异步分布式系统中，长时间收不到某进程消息即可判定其崩溃。
**答案：错**——异步系统无法区分"慢"与"死"，fail-stop 只能在同步系统用时限检测。

**简答｜** 比较同步/异步分布式系统；Pepperland 协定的两个变体各说明什么？
**答案要点**：同步=执行时间/消息延迟/漂移率均有界（数据库、实时游戏）；异步=均无界（Email、FTP），达成协定困难。变体一（通信兵不丢）：可就"谁冲锋"达成一致、不可就"冲锋时间"达成一致；变体二（通信兵可丢）：就冲锋/投降达成一致不可能（对应两将军问题）。

**简答｜** 故障模型如何分类？
**答案要点**：遗漏故障（进程崩溃、信道丢消息，良性）；随机故障/拜占庭（影响最大、难探知）；时序故障（仅同步系统）；屏蔽故障与可靠一对一通信两准则（有效性、完整性）。

## 第 3 章 时间和全局状态

### 知识点组 5｜物理时钟同步（漂移、正确性、三种方法）

【配套：《知识点整理》§3.2–3.4】

**判断｜** 若时钟集合在范围 D 内外部同步，则在范围 2D 内内部同步。
**答案：对**——内外部同步关系，必考数字。

**判断｜** Berkeley 算法中主机把本地时间直接发给从机。
**答案：错**——发送的是每个从机的**调整量**，且计算**容错平均值**。

**选择｜** Cristian 方法设置时钟为 t + Tround/2，精度为：A. ±min  B. ±(Tround/2−min)  C. ±Tround
**答案：B**；追问何时误差为 0：Tround = 2×min。

**选择｜** NTP 三种同步模式中精度最高的是：A. 组播  B. client/server  C. 对称
**答案：C**（对称模式保留双向时序信息）；组播用于高速 LAN、效率高精度低。

**简答｜** 什么是时钟正确性？
**答案要点**：漂移率有界；单调性（时间不回跳，make/日志依赖）；混合条件（单调+漂移有界+同步点跳跃前进）。反例：千年虫回跳、电池不足漂移突增。

**简答｜** 简述 NTP 的层次结构与偏移估计方法。
**答案要点**：strata 分层，主服务器直连 UTC，子网可重配置；四个时间戳得 **oi = [(Ti−2−Ti−1) + (Ti−3−Ti)]/2**，**di = (Ti−2−Ti−1) + (Ti−Ti−3)**，延迟越小样本越优。

### 知识点组 6｜逻辑时钟与向量时钟（计算重点）

【配套：《知识点整理》§3.5–3.8】

**判断｜** Lamport 时钟满足：L(e) < L(e') 则必有 e → e'。
**答案：错**——只有 e→e' ⇒ L(e)<L(e') 单向成立；反向不成立（Lamport 不捕获因果）。

**判断｜** 向量时钟的大小关系与 happens-before 关系完全等价。
**答案：对**——V(e)<V(e') ⟺ e→e'；V(e)∥V(e') ⟺ e∥e'。

**选择｜** Lamport 接收消息事件的正确时间戳是：A. max(Lj,t)  B. max(Lj,t)+1  C. Lj+1  D. t+1
**答案：B**——先 max 再 +1（LC2 触发 LC1）；向量时钟则是逐分量 max（不 +1 到整体，自身分量在事件前已 +1）。

**计算｜** 给三进程时空图（初值 0、若干消息箭头），求各事件 Lamport 时钟与向量时钟。
**通用步骤**：Lamport——本地/发送 +1，接收 = max(本地, t)+1；向量——事件前 Vi[i]+1，发送携全向量，接收逐分量 max。同值 ≠ 同一事件；全序需 (T, 进程号)。**同值不同链路是判断题高频陷阱**（如 b=2、d=2 并存）。

**简答｜** 为什么需要全序逻辑时钟？物理意义？
**答案要点**：不同进程可能产生相同 Lamport 时间戳；加进程标识符 (Ti, i) 破对称获得全序；无物理意义但实用（如全序互斥算法）。

### 知识点组 7｜割集、一致全局状态与快照算法

【配套：《知识点整理》§3.9–3.10】

**判断｜** 快照记录的各进程状态一定来自同一物理时刻。
**答案：错**——各状态可来自不同物理时刻，但构成**一致的全局状态**（一个可能的合理现实）。

**判断｜** Chandy-Lamport 快照中，进程记录自身状态后必须先向所有外出通道发 marker 再发其他消息。
**答案：对**——发送规则；接收规则：首收 marker → 记录状态 + 该通道记空 + 开始记录其他入通道；非首收 → 该通道记录 marker 之后收到的消息。

**选择｜** 算法对通道的假设是：A. 单向、FIFO、不故障  B. 双向可乱序  C. 无假设
**答案：A**——FIFO 防止 marker 超前应用消息导致丢失；无故障+强连通防无限等待。

**分析｜** 给时空图与若干割集，判断割集一致性。
**通用步骤**：逐条消息检查——**只允许"飞出去"（发送∈C、接收∉C），不允许"飞进来"（接收∈C、发送∉C）**；出现后者即不一致。

**简答｜** 为什么快照算法能记录一致的全局状态？
**答案要点**：反证法证明 ei→ej 且 ej∈C ⇒ ei∈C：若 ei 未被记录则它在 pi 发 marker 之后，由 FIFO 所有 recv(mi) 在 marker 后，故 ej 也在 marker 后不被记录，矛盾。

**简答｜** 走一遍两进程 $1000/$50 交易的快照例：为什么记录的总资产守恒？
**答案要点**：在途消息（订单）被记入**通道状态**，进程状态+通道状态合计与真实状态一致；这正是必须记录通道状态的原因。

### 知识点组 8｜分布式调试与全局状态谓词

【配套：《知识点整理》§3.11】

**判断｜** 稳定谓词一旦为 True，其后所有可达状态恒为 True。
**答案：对**——如死锁、系统终止。

**简答｜** 安全性（safety）与活性（liveness）各是什么含义？各举一例。
**答案要点**：safety=坏事永不发生（死锁自由、无孤儿对象、共识不决定不同值），有限步骤可确认违反；liveness=好事终将发生（无饥饿、最终一致），有限步骤无法确认违反。

**分析｜** 给一致全局状态网格与各状态谓词值，判断 possibly / definitely。
**通用步骤**：possibly = 存在**一个** True 状态即可；definitely = 每条从初态到终态的路径**都经过** True（有一条全 False 路径即不成立）。逐层扫描网格。

**分析｜** 监控器收到带向量时间戳的状态 S=(s1..sN)，如何判定 S 一致？
**答案要点**：CGS 条件——V(si)[i] ≥ V(sj)[i] 对所有 i,j 成立（每个状态对自己分量的计数最大）。

## 第 4 章 协调和协定

### 知识点组 9｜分布式互斥

【配套：《知识点整理》§4.2】

**判断｜** 中央服务器算法同时满足安全性、活性和顺序要求。
**答案：错**——异步系统中请求到达次序不定，**不满足顺序**；环算法同样不满足顺序。

**判断｜** Maekawa 投票算法可能死锁。
**答案：对**——V1={p1,p2}, V2={p2,p3}, V3={p3,p1} 三进程并发请求，各自投自己一票、互等对方；改进：优先级/时间戳/超时。

**选择｜** 组播+逻辑时钟算法（Ricart & Agrawala）进入临界区的消息数为：A. 2(N−1)  B. N  C. 3√N
**答案：A**——(N−1) 请求 + (N−1) 应答；同步延迟仅 1 个消息传输。

**选择｜** 互斥算法中满足全部三项要求（安全/活性/顺序）的是：A. 中央服务器  B. 环  C. 组播+逻辑时钟
**答案：C**。

**简答｜** 分布式互斥的基本要求与性能指标？
**答案要点**：安全性（临界区最多一人）、活性（无死锁饥饿）、顺序（与请求 hb 序一致）；带宽、客户延迟、同步延迟（切换延迟）、吞吐率。

**简答｜** 画表比较四种互斥算法。
**答案要点**：中央（enter 2 消息/exit 1、同步延迟 2 消息、SPOF）；环（令牌常耗带宽、同步延迟 1~N）；组播+LC（2(N−1)、同步延迟 1 消息）；Maekawa（3√N、投票集两两相交、可能死锁）。

### 知识点组 10｜分布式选举

【配套：《知识点整理》§4.3】

**选择｜** Bully 算法适用于：A. 异步系统  B. 同步系统（超时检测故障）  C. 仅环形拓扑
**答案：B**——通道可靠、允许进程崩溃。

**判断｜** 基于环的选举算法具备容错能力。
**答案：错**——一个节点故障则环断裂；最坏 3(N−1) 条消息，最好周转 2N。

**计算｜** Bully 算法最好/最坏消息数各是多少？何时出现？
**答案**：best = N−2（次大进程发起，直接广播协调者消息）；worst = O(N²)（最小进程发起，依次触发 N−2 次选举）。"霸道"得名：最大 id 者即使非原协调者也强行当选。

**简答｜** 描述环选举的消息流转。
**答案要点**：发起者发 {elect, id}；id 更大则转发并标记参与者；id 更小且非参与者则换成自己 id 转发；id 相等→当选，发 {elected, id}，回到发起者结束。

### 知识点组 11｜组播通信

【配套：《知识点整理》§4.4】

**判断｜** B-multicast 满足可靠组播的协定性质。
**答案：错**——sender 中途崩溃则其余进程可能收不到；可靠组播保证"要么全部要么全不"。

**判断｜** 统一协定允许进程在投递消息后崩溃。
**答案：对**——但只要它投递过，组内所有正确进程终将投递；洪泛算法中"先转发再投递"满足统一协定，交换两行即破坏。

**选择｜** 可靠组播需额外保证的三性质是：
**答案：完整性**（至多投递一次）、**有效性**（自己终将投递）、**协定**（一投递则全投递）。

**简答｜** 如何用 B-multicast 实现可靠组播？代价？如何用 IP 组播实现？
**答案要点**：洪泛——收到非重复消息即重发给全组再 R-deliver，满足三性质但每消息累计 |g|² 条；IP 组播+捎带确认+否定确认（NACK）+保留队列：序号 m.S=R+1 投递、≤R 丢弃、>R+1 缓存并 NACK 请求重传。

**简答｜** FIFO、因果、全序三种有序组播分别如何实现？
**答案要点**：FIFO——每进程序号+保留队列；因果——向量时钟，投递前验证因果前驱已投；全序——sequencer 定序器分配序号，或 ISIS 算法（各收者建议 max(A,P)+1、发送者取最大广播，冲突加 pid 破对称）。

### 知识点组 12｜共识、拜占庭与 Paxos

【配套：《知识点整理》§4.5】

**选择｜** 容忍 f 个拜占庭故障至少需要进程数：A. 2f+1  B. 3f  C. 3f+1
**答案：C**；若是崩溃故障的 Paxos acceptor 则为 **2f+1**（多数派相交）——两个数字必须分开记。

**判断｜** 三个进程（无数字签名）可以解决拜占庭协定问题。
**答案：错**——N≤3f 无解：两场景（司令正确/司令叛变）中 p2 无法分辨，对称性导致违反协定；加数字签名可解。

**判断｜** FLP 定理：网络可靠但允许哪怕一个节点失效的异步系统中，不存在确定性共识算法。
**答案：对**。

**简答｜** 共识、拜占庭将军、交互一致性如何相互构造？三者要求？
**答案要点**：要求均为终止/协定/完整性（BG 的完整性=司令正确则采用其值；IC 的完整性=pi 正确则第 i 分量=vi）。构造：BG 跑 N 次（轮流当司令）→ IC；IC 取 majority → 共识；司令分发值+全员跑共识 → BG。

**简答｜** 四个将军（N=4, f=1）如何两轮达成一致？
**答案要点**：第一轮司令发值给各中尉；第二轮各中尉转发收到的值给其他人；各取 majority。司令正确→一致且=司令值；司令叛变→一致取默认值。

**简答｜** 描述 Basic Paxos 的角色与两阶段；为何会活锁、如何缓解？
**答案要点**：Proposer/Acceptor/Learner；prepare(N)→promise(N,(n,U))，U=已接受最高编号提案；凑齐 quorum 后 accept(N,W)，W=promise 中最高编号已接受的值（无则任取）→accepted（记稳定存储）。dueling proposers 相互压制→换更大编号重试，Multi-Paxos 用稳定 leader 缓解。

**分析｜** 给 prepare/promise 交错执行图，写出各 Acceptor 状态与最终选中的值。
**通用步骤**：每个 Acceptor 只记两个量（已承诺的最大编号、已接受的最高编号提案）；promise 条件 = N 更大；accept 条件 = N ≥ 已承诺编号；最终值看是否被多数派接受。

## 第 5 章 事务和并发控制

### 知识点组 13｜事务 ACID 与串行等价（计算重点）

【配套：《知识点整理》§5.1–5.4】

**选择｜** 不构成冲突的操作组合是：A. read-read  B. read-write  C. write-write
**答案：A**——效果与次序无关。

**判断｜** ACID 中的 C（一致性）就是 CAP 定理中的 C。
**答案：错**——ACID-C 是应用层完整性约束（借贷平衡）；CAP-C 是副本间实时一致（可线性化）。同理可线性化 ≠ 可串行化。

**判断｜** 严格两阶段加锁中所有锁必须保持到事务提交（或放弃）之后。
**答案：对**——目的：防脏读与过早写；普通 2PL（释放后不得再申请）目的：防更新丢失与不一致检索。两级目的别混。

**简答｜** 什么是串行等价？充要条件？如何防止脏读与过早写？
**答案要点**：交错效果等价某串行序；充要条件=所有冲突操作对按相同次序执行；脏读→可恢复性（推迟提交）；过早写→write 等前面写同一对象的事务结束；临时版本支撑放弃即清除。

**计算｜** 给 T、U（或 T、U、V）操作序列与一个交错执行，判断是否串行等价；或构造串行等价的交错。
**通用步骤（冲突对次序表法）**：①列出全部冲突对（同对象、至少一写、不同事务）；②每对标注"先 T 后 U / 先 U 后 T"；③全同向→串行等价（即该方向的串行序）；④出现反向→非串行等价。构造题：选定串行序（如 T→U→V），保持各事务内部相对顺序穿插排布，再回验方向。期末手写作业原题即此类型（最终 i=30,j=20 或 i=30,j=10）。

### 知识点组 14｜三种并发控制方法

【配套：《知识点整理》§5.5–5.8】

**选择｜** 对读操作占优的事务，最合适的方法是：A. 严格 2PL  B. 时间戳排序  C. 向前验证
**答案：B**——静态定序；写操作占优则 2PL 更优（动态定序）。

**判断｜** 乐观并发控制的向前验证允许在验证阶段启动新事务。
**答案：错**——新事务读集可能与验证事务写集冲突；向后验证无此限制但需保存已提交事务写集。

**判断｜** 锁超时是解除死锁最常用的方法之一；超时锁变"可剥夺锁"。
**答案：对**——缺点：可能误伤长事务（无死锁也可能被剥夺放弃）。

**简答｜** 比较锁、乐观、时间戳三种并发控制。
**答案要点**：2PL——执行中动态定序、等待可能死锁、写优；时间戳——启动时静态定序、冲突立即放弃无死锁、读优；乐观——三阶段（工作/验证/更新）、冲突少时高效、验证只允许一个事务；前后两者悲观，乐观冲突多时代价大。附：向后验证查 Tv 读集∩Ti 写集（Ti 已提交），向前验证查 Tv 写集∩活动事务读集。

## 第 6 章 分布式事务

### 知识点组 15｜原子提交与两阶段提交协议

【配套：《知识点整理》§6.1–6.5】

**选择｜** 2PC 无故障时 N 个参与者的消息数（不含 haveCommitted）：A. N  B. 2N  C. 3N
**答案：C**——N 个 canCommit + N 个投票 + N 个 doCommit。

**判断｜** 2PC 中参与者投 Yes 后、收到决议前可以单方面放弃。
**答案：错**——此为"不确定（uncertain）"状态，只能等协调者或发 getDecision；而 canCommit 未到/未投票时才可单方面放弃。

**判断｜** 2PC 的三大缺陷是同步阻塞、单点故障与数据不一致。
**答案：对**——手写作业原题；改进：3PC（加预提交阶段，参与者可依自身与其他参与者状态判断结局）；恢复：日志+getDecision/doCommit/doAbort。

**简答｜** 2PC 的设计动机、五个基本操作、两阶段过程。
**答案要点**：动机=允许任意参与者自行放弃；五操作 canCommit/doCommit/doAbort/haveCommitted/getDecision；阶段一投票（投 Yes 前先持久化对象），阶段二按票决定（全 Yes 且无故障→doCommit，否则向投 Yes 者发 doAbort）。

**分析｜** 逐一分析四类消息丢失的后果与处理。
**答案要点**：canCommit 丢→参与者超时单方放弃；Yes/No 丢→协调者超时放弃并通知投票者（悲观）；doCommit 丢→参与者 getDecision 重试直到答复；haveCommitted 丢→不影响正确性；参与者投 Yes 后崩溃→重启仍能正确提交（已持久化）。

**简答｜** 原子提交与共识的区别？
**答案要点**：共识容忍少数节点崩溃（法定人数即可）；原子提交**任一参与者崩溃都必须放弃**（一票否决，不可取多数）。

### 知识点组 16｜分布式死锁与事务恢复

【配套：《知识点整理》§6.6–6.7】

**选择｜** 边追逐方法检测涉及 N 个事务的死锁需要消息数：A. N−1  B. 2(N−1)  C. N²
**答案：B**——每转发一条 probe 需 2 个消息（对象服务器→协调者→等待对象的服务器），经 N−1 次转发。

**判断｜** 集中式死锁检测依赖单一服务器，可靠性差、收集局部等待图代价高。
**答案：对**——分布式替代即边追逐（probe 探测环），解除时按事务优先级放弃避免过度放弃。

**简答｜** 什么是意图列表与日志？各状态恢复后做什么？
**答案要点**：意图列表记录事务修改对象 <ObjectID, 位置>（提交时换版本、放弃时删临时版本）；日志=对象值+事务状态+意图列表+检查点。恢复表：协调者 prepared→doAbort（未决定）；协调者已提交→重发 doCommit；参与者已提交→haveCommitted；参与者 uncertain→getDecision；参与者 prepared→单方面放弃；完成→无操作。

## 第 7 章 复制

### 知识点组 17｜四种一致性

【配套：《知识点整理》§7.3】

**选择｜** 主动复制（全序可靠组播）具备：A. 可线性化  B. 顺序一致性  C. 因果一致性
**答案：B**——全序未必与实时序相同；被动（主备份）复制才是可线性化。

**判断｜** 因果一致性要求所有写操作（含并发写）全局同序可见。
**答案：错**——只要求**因果相关**的写同序；并发写可不同序。

**分析｜** 给两客户的读写序列与观测结果，判断满足哪级一致性。
**通用步骤（从强到弱逐级检验，过一层停）**：①线性化——读是否返回**实时最近**的写；②顺序一致——各客户**自身程序序**是否保持（跨客户可重排）；③因果一致——因果相关的写是否同序、并发写乱序可接受；④最终一致——只看是否收敛。经典例：客户1 写 B(x,1)→A(y,2)，客户2 读 y=2 再读 x=0 → 程序序与单副本语义都破坏，连顺序一致都不满足；若读 y=0、x=0 则顺序一致但不线性化。

**简答｜** CAP 原理与 BASE 理论？
**答案要点**：C/A/P 三者最多取二；P 成立时 C 与 A 二选一（分区下同步则失可用、各干各的则失一致）；BASE=基本可用+软状态+最终一致。

### 知识点组 18｜主动/被动复制与单拷贝串行化

【配套：《知识点整理》§7.4–7.5】

**判断｜** 可用副本复制在"副本管理器集无变化"前提下可保证单拷贝串行化。
**答案：对**——执行中发生故障/恢复则可能破坏（锁失效），需**本地验证**：提交前检查已访问副本集是否变化，变化即放弃。

**简答｜** 比较被动复制与主动复制的事件次序与一致性。
**答案要点**：被动——请求只发主，主定序执行，更新+应答+标识发备份收确认后响应→可线性化；主动——前端全序可靠组播到全体，各 RM 同序执行、无需协定阶段→仅顺序一致。

**简答｜** 什么是单拷贝串行化？"读一个/写所有"的内容与局限？
**答案要点**：复制对象上事务的效果同每对象单副本逐一执行；读一=单个 RM 执行读，写所有=全部 RM 执行写；局限=任一 RM 崩溃即不可行，故有可用副本复制+本地验证。

### 知识点组 19｜Gossip 系统（讲义原题区）

【配套：《知识点整理》§7.6】

**判断｜** Gossip 系统保证客户总能读到最新数据。
**答案：错**——两个保证是：①数据能反映客户**已观测到**的更新（随时间推移每用户获得一致服务）；②副本间松弛一致、最终全收敛。客户**可能**读到过时数据。

**简答｜** 写出 Gossip 副本管理器的六个关键数据结构及作用。
**答案要点**：值 val（应用状态）；值时间戳 val.ts（已稳定更新）；副本时间戳 replica.ts（已收到的更新）；更新日志 log（不稳定更新待处理）；已执行操作表 executed（防重复）；时间戳表 tableTS（判断更新是否全体生效、支持日志删除）。

**简答｜** Gossip 查询与更新的执行条件各是什么？
**答案要点**：查询条件 **q.pre ≤ rm.val.ts**，不满足则进保留队列**阻塞**（如 (2,1,0) > (1,0,0)）；更新稳定性条件 **u.prev ≤ rm.val.ts**，不满足则推迟（保证因果次序）；gossip 接收时若发送方 replica.ts ≤ 本地则丢弃。

**分析｜** 三副本推演：fe0 更新 x=1 → fe1 更新 x=2（发给 rm2 的 gossip 丢失）→ fe0 更新 x=3；写出各 RM 状态变化，说明 rm2 如何保持因果次序。
**通用步骤**：更新五步（查重 executed→replica.ts[i]+1→构造 ts=prev 且 ts[i]=replica.ts[i]→记日志→回 FE merge）；rm2 收到 x=3（prev=(1,1,0)）时因 val.ts=(1,0,0) 不满足稳定条件**推迟**，先执行 x=2 再执行 x=3；日志删除条件 = 所有 RM 的 tableTS[i][c] ≥ r.ts[c]；fe0 连到落后的 rm2 查询会阻塞。完整推演见《Gossip讲义.docx》。

### 知识点组 20｜DFS 需求与文件服务体系结构

【配套：《知识点整理》§8.1–8.2】

**选择｜** 平面文件服务中除 create 外所有操作都幂等的原因是：
**答案：read/write 显式携带位置参数 i、无 open/close 与读写指针**——因此也是无状态服务器（重复调用安全）。

**简答｜** 文件服务体系结构三个组件及作用。

**简答｜** 分布式文件系统有哪些需求？
**答案要点**：透明性（访问/位置/移动/性能/伸缩）、并发更新、文件复制、异构性、容错（幂等+无状态）、一致性（单拷贝更新语义）、安全（认证，Kerberos）、效率。

### 知识点组 21｜NFS 与 AFS

【配套：《知识点整理》§8.3–8.4】

**选择｜** NFS 文件句柄的组成：A. 文件系统标识符+i 节点数+i 节点产生数  B. 卷号+路径+版本  C. IP+端口+inode
**答案：A**；句柄对客户不透明，客户/服务器间传递。

**判断｜** NFS 服务器保存客户读写指针，属于有状态服务器。
**答案：错**——NFS 无状态：read/write 显式带 offset，每请求重新验证 UID（Kerberos）。

**判断｜** AFS 的回调承诺有"有效"与"取消"两种状态。
**答案：对**——其他客户修改文件时 Vice 把承诺置取消；客户重启或长期收不到回调也视为无效。

**简答｜** NFS 路径解析为什么由客户完成？如何完成？
**答案要点**：服务器不做路径名转换；客户对路径每一段发 lookup 请求，逐级将名字转换为文件句柄（例：/programs/pong.c 经根 inode→14 块→inode 7→23 块→inode 9→61 块）。

**简答｜** NFS 客户缓存如何保持一致性？
**答案要点**：每块带 Tc（上次验证时间）与 Tm（块修改时间）；有效条件 **T−Tc < t 或 Tmclient = Tmserver**；t 为更新间隔（文件 3~30s、目录 30~60s）——一致性与效率折衷，不能保证 UNIX 级一致性。

**简答｜** AFS 为什么可扩展性好？
**答案要点**：整体文件传输+本地磁盘整体缓存+回调机制——读多写少场景下客户与服务器交互显著减少（回调有效时不访问服务器），远优于轮询。

## 第 9 章 谷歌文件系统 GFS

### 知识点组 22｜GFS 架构、操作与一致性模型

【配套：《知识点整理》§9.1–9.8】

**判断｜** GFS 客户端与 chunk 服务器都应缓存文件数据以提高性能。
**答案：错**——都不缓存文件数据（流式读/工作集大；本地文件由 Linux 缓存管理），**客户端只缓存元数据**。

**判断｜** GFS Record Append 并发成功时结果是一致且确定的。
**答案：错**——append 是**确定但可能穿插不一致**（某副本失败重试成功后，失败区间不一致）；"一致但不确定"是并发 **Write** 的结果。

**选择｜** GFS 每个 chunk 的副本数至少为：A. 2  B. 3  C. 5
**答案：B**（3 个，跨机架）；chunk 大小 64MB。

**简答｜** 单一 Master 为什么不成为性能瓶颈？（五点，必背）
**答案要点**：①只存元数据不存数据（磁盘容量）；②元数据存磁盘+内存（磁盘 I/O）；③元数据内存装得下（内存容量）；④数据流不走 Master（带宽）；⑤客户端缓存元数据（CPU）；另：Master 快故可后台扫描（垃圾收集/块迁移/重复制）。

**简答｜** 描述写操作流程；数据流与控制流为何分离？
**答案要点**：问 Master 得句柄与副本位置→client 把数据推给**所有副本**存入缓存→发写命令给 Primary→Primary 定序→secondary 按序写→逐级应答→Primary 响应 client。数据流沿拓扑就近推送与控制流解耦，充分利用带宽。

**计算｜** 文件偏移 X=134,250,297 字节，chunk 64MB，求 chunk 索引与块内偏移。
**答案**：64MB=67,108,864B；134,250,297 = 2×67,108,864 + 32,569 → 索引 2（若从 1 计数则为 3）、块内偏移 32,569。

**分析｜** 两客户并发改写文件 F 的两个 chunk（A 尾 5 字节、B 头 5 字节），A 的 Primary 定序 M1→N1，B 的定序 N2→M2，分析副本终态。
**答案**：A 副本尾 5 字节="77777"，B 副本头 5 字节="66666"；每个 chunk 内由各自 Primary 唯一定序→副本间**一致**；两个 chunk 定序不同→用户写入交错→**不确定**（consistent but undefined）。即 GFS 放松一致性模型、以 Record Append 提供确定追加语义的动机。

**简答｜** 解释一致（consistent）与确定（defined）；列出写/追加各情形。
**答案要点**：一致=各副本读相同；确定=读到全部更新内容且不受并发写干扰。串行 Write 成功→defined；并发 Write 成功→consistent but undefined；append 成功→defined 但穿插不一致；失败→inconsistent。

## 第 10 章 P2P、DHT 及 Chord

### 知识点组 23｜一致性哈希、DHT 与 Chord

【配套：《知识点整理》§10.1–10.4】

**选择｜** 一致性哈希新增一个节点时平均需要搬家的键比例：A. 全部  B. 1/N  C. 1/2
**答案：B**——对比 hash%N：N 变则几乎全部映射失效（破坏单调性）。

**判断｜** Chord 的查询复杂度为 O(N)。
**答案：错**——用 Finger Table 后为 **O(log N)**；简单沿环逐跳查询才是 O(N)。

**选择｜** 节点 n 的指针表第 i 项是：A. successor[n+2^(i−1)]  B. n+i  C. predecessor(n)
**答案：A**（1 ≤ i ≤ m）；每跳选不超过目标的**最大表项**逼近。

**简答｜** 一致性哈希的四个条件？
**答案要点**：平衡性（均匀分布）、单调性（新缓冲加入不改变既有归属方向）、分散性（终端所见面不同时不致同内容异缓冲）、负载（同缓冲不致被映射为异内容）。

**简答｜** DHT 的主要思想四步。
**答案要点**：内容索引抽象为 (K,V)，K=Hash(key)、V=节点位置；全体 (K,V) 构成大 Hash 表；按 K 与节点 ID 映射规则把表分块分布（节点 ID 常为 IP 的 Hash）；查询按规则路由到负责节点。

**简答｜** Chord 的 Hash 表分布规则与抗 churn 机制？
**答案要点**：SHA-1 得 m 位节点 ID/键 ID，节点按 ID 排成逻辑环；(K,V) 存于 **Successor(K)**（K 起顺时针第一个节点）；节点加入：后继移交 <N 的键；退出/失效：指针表改指后继，每节点维护 **r 个后继的后继列表**替换失效后继；遗留拓扑失配问题（逻辑跳跨物理网络，时延大）。

**计算｜** m=6 的 Chord 环，节点 {1,8,14,21,32,38,42,48,51,56}，键 K=54 存于哪个节点？从 N8 查询至少几跳？
**答案**：Successor(54)=N56；N8 指针表 successor[8+1..8+32]={14,14,21,32,42,51}（8+32=40→42，注意环绕），取 ≤54 的最大项 51 → N51 → 54（1 跳后即达后继），共约 2 跳；一般结论：每跳逼近一半距离，跳数 O(log N)。

## 通用解题思路（跨题型）

**1. 性质判断题（选择/判断）——方向 + 反例法**
- 凡"若 A 则 B"先想反向是否成立：Lamport 时间戳、可线性化 vs 可串行化、2PL 两级目的、主动/被动复制一致性——单向性质说成双向即错。
- 绝对化表述（"一定""必然""所有"）多为错：去掉前提（同步/异步、副本集不变、无故障）的结论是重灾区。
- 数字模板成对记：容错个数（2f+1 崩溃 / 3f+1 拜占庭）vs 消息条数（2(N−1) 互斥、3N 2PC、2(N−1) 边追逐、3(N−1) 环选举、N−2 Bully、|g|² 洪泛）。

**2. 流程简答——定义 → 机制（分阶段编号） → 性质/复杂度 → 例子**
- 对比题先写维度再填表（互斥四算法、并发控制三方法、四种一致性、NFS vs AFS）。
- 协议题按阶段复述：2PC 两阶段五操作、快照两条规则、Paxos 两阶段四消息、Gossip 两个条件。

**3. 计算题——规则逐步走，写中间状态**
- 时钟题在每个事件旁写计算式（L=max(2,1)+1=3），出错仍有过程分；同值不同事件是陷阱。
- 串行等价永远用冲突对次序表：列对 → 标方向 → 全同向则等价；构造题定好串行序后回验。
- 协议消息数画时序图逐箭头数，口诀"一问一答=2 条、转发=2 条"。
- GFS 索引先换算 64MB=67,108,864B，注意索引从 0 还是从 1。

**4. 分析题——先结论、后依据，按"模型 → 假设 → 机制 → 现象 → 判定"五步**
- 一致割集只查一件事："飞出去可以、飞进来不行"。
- 一致性场景从强到弱逐级检验（实时序→程序序→因果序→收敛），第一层不满足即降级。
- 2PC 故障按"哪条消息丢/谁崩"对号入座恢复动作表；投 Yes 后不能单方放弃是核心约束。
- 算法推演（快照、Gossip、Paxos）老老实实逐事件模拟，单独列出各进程维护的状态量，最后验证目标性质（守恒/因果/协定）收尾。
