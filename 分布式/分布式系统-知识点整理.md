## 第 1 章 分布式系统的特征

### 1.1 构建分布式系统的原因（动机）【考点】

单机系统的能力天然有上限：算力不够、磁盘会坏、数据本来就是分散在不同人手里的。分布式系统的出现不是为了"更高级"，而是被下面这些现实逼出来的：

- **功能分离（Functional Separation）**：不同机器有不同的能力和用途，天然要分工——客户端管交互、服务器管数据；采集端和计算端分开。这是最古老的动机，三十年前用它拆出 C/S 结构，今天大模型推理用它拆出 Prefill 和 Decode 两个集群，动机完全一样。
- **固有的分布性（Inherent Distribution）**：有些东西"天生"就在一起不了。信息由不同的人在不同地方创建维护（Web 页面）；协作的人分布在各地（虚拟团队）；数据量单机根本装不下——例如训练一个 405B 参数的模型，混合精度 + Adam 状态约 6.48 TB，而单卡 H100 只有 80 GB，切开不是选项而是物理约束。
- **负载均衡与算力不均衡**：把计算负载摊到多台机器上，避免一台挤爆、其他闲置。
- **可靠性（Reliability）**：一台机器会坏，多台异地副本可以长期保存数据。
- **经济性（Economies）**：用大量廉价普通机器组出"超级计算机"，比买一台真超算便宜。

由此推出分布式系统的两个目标：**资源共享**（硬件、软件、数据、服务）与**协同计算**（并行计算、分布式计算）。

### 1.2 定义【考点】

教材（CDK）的定义要能默写：

> **分布式系统是这样一个系统：其组件位于网络上的计算机中，且组件之间只通过传递消息来通信和协调它们的行为。**

两个经典补充视角：Lamport 的调侃版——"我没听说过的某台机器崩溃，导致我的工作无法完成"（强调故障是常态且不可见）；Tanenbaum 的版本——"一组自治的计算元素，对用户看起来像一个一致的系统"（强调透明性目标）。三个定义合起来正好刻画了分布式系统的两面：**靠消息协作** + **装作一台机器**。

### 1.3 三个基本特点【考点】

这三个特点是判断"一个系统算不算分布式、会遇到什么麻烦"的根，后面每一章几乎都从它们出发：

1. **并发性（Concurrency）**：多个程序（进程/线程）同时在跑、共享资源。麻烦在于并发访问同一份数据会互相干扰——所以有第 5 章事务与并发控制。
2. **无全局时钟（No global clock）**：每台机器有自己的时钟，谁也无法精确同步。麻烦在于"谁先谁后"不能靠看表判断——所以有第 3 章逻辑时钟和事件排序。
3. **故障独立性（Independent failure）**：一个进程坏了，系统不保证其他进程知道。麻烦在于你分不清对方是"慢"还是"死了"——所以有第 4 章的共识与故障检测。

课件用大模型训练印证了第 3 点：16384 张卡靠同步 barrier 强行耦合，平均约 3 小时全体停摆一次——一旦放弃故障独立性，故障就被放大。

### 1.4 举例

要能各举一例并说出其分布式特点：Web 搜索（Google：GFS 文件系统 + Spanner/Bigtable 存储 + Chubby 锁 + MapReduce 计算，失效是常态）、MMO 游戏（低延迟 + 共享世界一致视图）、金融交易（基于事件的分布式系统，FIX 协议）、区块链（分布式账本，共识、容错 vs 性能的取舍）、语音（集中 vs 对等、中转 vs 直连）、数据库（scale-up 单机变强 vs scale-out 加机器）、AI 大规模训推（万卡集群、联邦学习）。

### 1.5 挑战【考点】（7 个）

挑战就是"分布式比单机难在哪"，每一条要能说出问题本身 + 一个应对手段：

1. **异构性 Heterogeneity**：网络协议、硬件（字节序、ISA）、操作系统 API、编程语言、开发者的实现都不同。核心手段是**中间件**——一层软件屏蔽底层差异（如 Java RMI、DB proxy）；移动代码/虚拟机也是应对异构的（虚拟机分 ISA 级、HAL 级、OS 级、库级、应用级五类）。
2. **开放性 Openness**：系统能否被扩展或以不同方式重新实现。关键在于**公开接口**：API、RPC、Restful、标准序列化。类比 POSIX：符合标准接口的 OS 之间移植应用就容易。
3. **安全性 Security**：三个目标——机密性（防未授权访问，ACL/加密）、完整性（防篡改，校验和/签名）、可用性（防服务干扰，防 DoS）。
4. **可伸缩性 Scalability**：规模变大后性能不崩。四个设计要点：控制物理资源代价（随用户数增长不超过 O(n)）、控制性能损失（如 DNS 查询 O(log n)）、防止资源耗尽（IP 地址枯竭）、防性能瓶颈（分区、缓存、复制）。课件用大模型集群的例子升级了理解：网络本身就不均匀（机内 NVLink 900 GB/s vs 机间 IB 50 GB/s），上层算法必须感知拓扑。
5. **故障处理 Failure handling**：检测（校验和；但远程服务器是否真坏了很难确切知道）、屏蔽（重发、备份服务器）、容错（屏蔽不了就告知用户让其选择）、恢复（操作日志）、冗余（DNS 副本表）。
6. **并发性 Concurrency**：正确性（多进程访问共享数据不出不一致，DB transaction）+ 性能（并发下仍要快）。
7. **透明性 Transparency**（8 种，易考选择/判断）：让"分布"这个事实对用户不可见，用户专心做自己的事。8 种分别是：**访问**（本地远程同一套操作，如 NFS）、**位置**（不用知道资源在哪，如 URL）、**并发**（多人同时用互不干扰，如 DB/ATM）、**复制**（不知道有多个副本）、**故障**（有故障仍能完成任务）、**移动**（资源/用户移动不影响操作）、**性能**（系统可自动重配置改善性能，如 auto-scaling）、**扩展**（扩大规模不改结构与算法，如无状态设计）。

### 1.6 RPC 远程过程调用

**为什么需要 RPC**：直接用 socket 写分布式程序很痛苦——消息边界要自己定（TLV？）、两边语言可能不同、字节序不一致、每次都要重写一遍这些活。RPC 的思路是在 socket 之上再加一层，让"调用远程函数"写起来和调用本地函数一模一样。

**工作流程**（要能按序描述）：
1. 客户端正常调用一个本地函数——实际上是调用**客户 stub**（桩）；
2. stub 把参数**打包（marshalling / 序列化）**成网络消息（含过程名）；
3. OS 把消息发给服务器；服务器 OS 收到后交给**服务器 stub**；
4. stub 解包（unmarshalling）参数，调用真正的服务函数；
5. 结果沿原路反向返回（stub 打包返回值 → 回到客户 stub 解包返回给调用者）。

**要点**：
- **Stub 由编译器生成**：输入是 IDL（接口定义语言，描述参数/返回类型），输出是两端的打包/解包代码。gRPC 的 `.proto` 文件 + protoc 就是这套机制。
- **数据表示差异**是 RPC 的核心难题：远程机器可能用不同语言、不同类型宽度、不同字节序、不同对齐方式；且程序里数据有指针、链表、树，而网络传输是线性的——指针无意义，结构必须扁平化。解决：约定标准的外部数据表示（Sun XDR、CORBA CDR、Protobuf、JSON 等）。

## 第 2 章 系统模型

### 2.1 三类模型【考点】

"系统模型"就是把纷繁的真实系统抽象成几类，让我们能**在模型上推理正确性**。三层抽象从具体到一般：

- **物理模型**：描述硬件组成——什么计算机、怎么互连。演变：80 年代 LAN 上的早期系统（静态、分立、自治）→ 90 年代集群 → 当代的移动计算（节点会动，要服务发现）、普适计算（嵌进物品）、云计算（一组节点提供服务）。
- **体系结构模型**：不管硬件细节，只看"有哪些组件、各自干什么、怎么连"。
- **基础模型**：只抓所有分布式系统共有的最本质属性，形式化为三个模型：**交互模型、故障模型、安全模型**。

### 2.2 体系结构模型【考点】

体系结构模型回答四个问题：**通信实体是什么？用什么范型通信？扮演什么角色？放在物理设施的哪里？**

**（1）通信实体**：面向系统的视角是进程/线程/节点；面向问题的视角是对象（Java RMI、CORBA）、组件（对象 + 显式声明的依赖）、Web 服务、微服务。

**（2）通信范型**——按耦合程度递减理解：
- **进程间通信**：套接字、多播、消息传递，最底层。
- **远程调用**：请求-应答协议、RPC、RMI，最常用，双向。
- **间接通信**：前两种都有两个限制——**空间耦合**（发送者必须知道接收者是谁）和**时间耦合**（双方必须同时在线）。间接通信把这两个耦合都解掉：**组通信**（一对多）、**发布-订阅**（生产者消息经中间件路由给需要的消费者，如 RabbitMQ/MQTT）、**消息队列**（点到点）、**分布式共享内存 DSM**（物理分离的内存抽象成一个共享地址空间，隐藏消息传递）、**元组空间**（把结构化数据放进持久的元组空间，进程可读可取，如 Linda/JavaSpace）。

**（3）角色**——两种最基本的组织方式，也是第 1 章参数服务器 vs Ring AllReduce 的理论原型：
- **C/S**：简单直接；缺点是伸缩性封顶在服务器能力和带宽上（web/ftp/email）。
- **P2P**：观察到普通节点已具备能力和带宽，挖掘它们让服务能力随用户数一起增长；代价是管理难（节点动态、路由、QoS、安全）。例子 BitTorrent、eDonkey、IPFS。今天的 P2P 形态：区块链（每节点全量副本，靠共识一致，吞吐低）、内容分发（按内容寻址）、集合通信（NCCL Ring AllReduce——跑在机房里的结构化 P2P，无中心瓶颈但必须同步）。判断标准：**靠局部规则达成全局目标、没有中心，就是 P2P**。

**（4）放置**：实体如何映射到物理设施——多服务器映射（Ceph 哈希、HDFS 副本策略"2 同机架 1 异机架"）、**缓存**（前向在客户端侧、反向在服务器侧，如 Squid/CDN）、**移动代码**（把代码送到客户端执行：Applet → 今天的 WASM、边缘函数、eBPF、数据库 UDF；共同问题始终是异构 + 安全）、**移动代理**（代码带着数据在机器间穿梭——因要求宿主执行来路不明的代码而失败，演化成今天的 VM/容器在线迁移和计算卸载；教训：**信任边界决定计算能放到哪**）。

**（5）体系结构模式**：**分层**（复杂系统垂直分成服务层：平台→中间件→应用）、**层次化 tiered**（从应用视角组织，如 web 应用的多层）、**瘦客户**（本地只有轻量 GUI，计算在远端，如远程桌面/VDI）。

### 2.3 交互模型【考点】

交互模型研究"进程之间交互时会遇到什么客观限制"。两个根源：

- **通信通道性能**：三个指标——**延迟**（第一比特从发出到到达的时间，含访问网络和 OS 通信服务的时间）、**带宽**（单位时间可传输的信息总量）、**抖动**（传输时间的变化值；流媒体要稳定速率，所以怕抖动）。
- **没有全局时钟**：每台计算机有独立内部时钟，与绝对时间有偏移；**时钟漂移率**刻画偏离绝对参考时钟的快慢；可用 ntp、GPS 校时。

由此把系统分成两种（本课程最重要的二分法，第 4 章共识的不可能性结果就建立在它上面）：

- **同步分布式系统**【考点】：对时间有严格假设——每步执行时间有上下界、消息传输时间在已知范围内、时钟漂移率有界。可预期。例子：分布式数据库、实时在线游戏、电信系统。
- **异步分布式系统**【考点】：完全没有可预测的时限——执行速度、消息延迟、漂移率都可能任意。**现实中更常见**（Email、FTP、CDN）。后果：**达成协定非常困难**——你发消息后等不到回复，永远分不清对方是慢还是死了。

**Pepperland 协定**（思想实验，注意与两军问题区分）：
- 假设通信兵**不会被捕获**：红蓝两师能否就"谁先冲锋"达成一致？**能**——只关心结论，与等待多久无关。能否就"冲锋时间"达成一致？**不能**——通信兵若迟到太久，约定的时刻已失效（这就是异步系统里时间约定的不可靠）。
- 假设通信兵**可能被捕获**（引入遗漏故障）：能否就冲锋/投降达成一致？**Never**——无论如何设计确认机制，最后一条消息总能被捕获，双方永远不能确定对方收到了。这就是两将军问题/TCP 三次握手的根本困境。

### 2.4 故障模型【考点】

故障模型的意义：把"可能怎么坏"精确定义和分类，才能分析故障影响、设计容错。按 Hadzilacos & Toueg 分类：

- **遗漏故障（Omission）**：该做的没做。
  - 进程遗漏：**崩溃 crash**。fail-stop 崩溃在**同步系统**里可以靠超时检测出来（过了时限没响应即认定崩溃）；在**异步系统**里不行——长时间没消息也可能只是慢（这个区别第 4 章会反复用到）。
  - 通信遗漏：发送丢失、接收丢失、通道丢失。属于良性故障（不撒谎，只是丢）。
- **随机故障（Arbitrary，即拜占庭故障）**：该做的不做、不该做的却做——比如对过程调用返回一个错误值。影响最大、最难探知。信道上少见（靠校验和、序号能防住大部分）。
- **时序故障（Timing）**：只在**同步系统**中存在（响应超出了时间界）；异步系统没有时间保证，自然无此类故障。

**屏蔽故障（Masking）**：系统组件是层层构建的，用有故障的底层组件构造出可靠的高层服务是可能的。一对一通信可靠性的两个判据【考点】：**有效性 Validity**（发送端缓冲区的消息最终到达接收端缓冲区——不丢）、**完整性 Integrity**（收到的消息与发送的一致，且没有消息被发两次——不重不错）。

### 2.5 安全模型

保护对象的安全性 = 进程安全 + 信道安全 + 对象安全。对象保护两手段：**访问权限 ACL**（服务端规定谁能访问）与**权能 capability**（用户手里持有的访问凭证）。

主要威胁要能举例：对进程——伪造调用（CSRF）、伪造结果（钓鱼）；对信道——拷贝/篡改/填充、**重放**（例：重发一条转账请求造成重复转账，所以消息要带物理+逻辑时间戳）；另有 DoS（海量请求打垮服务器）和移动代码（木马）。

对策：加密与共享密钥（密码学是基础）、认证、**安全通道**（知道对方身份 + 数据私密完整 + 时间戳防重放）。HTTPS 流程要点：证书链（终端证书 ← 中间 CA ← Root CA）→ 握手协商对称密钥（pre-master 三个随机数）→ 会话数据全部加密。

## 第 3 章 时间和全局状态

> 本章主线：物理时钟靠不住（3.2–3.4）→ 那就定义与物理无关的逻辑时钟来排序事件（3.5–3.8）→ 排序能力进而让我们能"拍下"分布式系统的全局状态（3.9–3.10）→ 拍了快照就能在系统上判断性质、做调试（3.11）。

### 3.1 时钟、事件和进程状态【考点】

模型假设【考点】：每个进程在单处理器上执行、进程间不共享内存、**只靠消息通信**。在这个模型上定义三个对象：

- **事件**：一个通信动作（发/收消息）或进程状态转换动作。
- **进程历史** hi = ⟨e₀, e₁, e₂, …⟩：进程 pi 上按发生先后排列的事件序列。
- **进程状态**：该进程所有变量的值 + 相关本地 OS 环境中对象的值。

时间基准本身也有讲究：天文时间（太阳秒）不够稳定 → **TAI 国际原子时**（铯原子 9 192 631 770 次振荡定义为 1 秒）→ **UTC**（原子时基础上加闰秒，与天文时间对齐；2035 年起拟停用闰秒）。

### 3.2 时钟漂移及产生原因【考点】

每台计算机的时钟是靠晶振计数得到的独立硬件。晶振频率有制造误差，还随温度、老化变化，于是各机器的时钟走得**不一样快**：时钟与绝对时间的差叫偏移，偏离的速率叫**时钟漂移率**。这就是"分布式系统没有全局时钟"这一特点的物理来源——不是没人去同步，而是同步完很快又漂走。

### 3.3 内部/外部物理时钟同步、时钟正确性【考点】

- **外部同步**：以权威外部时间源（UTC）为基准，时钟 Ci 与 UTC 的偏差保持在范围 D 内。
- **内部同步**：没有外部源，系统内时钟互相之间偏差在 D 内。
- **关系**：范围 D 内外部同步 ⇒ 范围 **2D** 内内部同步（直觉：每台都与 UTC 差不超过 D，任意两台互差不超过 2D）。
- **时钟正确性**三种含义【考点】：
  1. **漂移率有界**：漂移在已知范围内；
  2. **单调性**：时间值不回跳——make 增量编译、日志、计时器都依赖它；闰秒问题（leap smear 把 1 秒摊到 24 小时，宁可短暂偏离 UTC 也不让时钟回跳）破坏的正是这一条；
  3. **混合条件**：单调 + 漂移有界 + 同步点只许向前跳。
- 时钟故障两类：崩溃故障（彻底停摆）、随机故障（如"千年虫"把 2000 年记成 1900、电池不足导致漂移率突增）。

### 3.4 物理时钟同步的三种方法【考点】

共同背景：**为什么不给每台电脑装 GPS？** 贵、室内收不到信号；实际做法是权威时间源（园区级 GPS+原子钟）+ 逐级分发（NTP strata / PTP）。几种经典方法按假设从强到弱排列：

**方法一：同步系统中的直接同步**。已知消息传输时间的不确定性 u = [min, max]。若对方在时刻 t 发时间过来，接收方该把钟设成多少？设 t+min 偏差至多 u、设 t+max 偏差可能为 u，**设 t+(max+min)/2 时偏差至多 u/2——取中点最优**。

**方法二：Cristian 方法**（有一个时间服务器 S 作外部源）：
- 客户 p 发请求（记下发送与接收时刻），服务器在应答里放当前时间 t；p 算出往返时间 Tround，把自己的钟设为 **t + Tround/2**。
- 直觉：请求和应答各占 Tround 的一半，服务器填 t 时应答大约还要走 Tround/2。
- **精度：±(Tround/2 − min)**【考点】——真实时间必落在 [t+min, t+Tround−min] 区间内，区间宽度即误差上界。理想情况 Tround = 2×min 时误差为 0。前提：往返时间远小于所需精度（否则区间太宽没用）。

**方法三：Berkeley 算法**（内部同步，没有外部 UTC 源，例如一批精度相近的机器互相对齐）：
- 主机周期性轮询各从机的时钟值；
- 主机计算**容错平均值**——先丢弃偏离过大的值再取算术平均（防一台坏钟带偏全体）；
- 主机给每台从机发**调整量**（渐变地拨，而不是直接设成目标值，保持单调性）。

**方法四（提纲并列）：NTP 网络时间协议**：
- 设计目标：让 Internet 上的用户与 UTC 外部同步；高可靠（冗余服务器、冗余路径，连接丢失可处理）；可扩展（大量用户可频繁同步抵消漂移）；安全（防恶意干扰）。
- **协议结构**：分层 strata——主服务器（stratum 1）直连 UTC 源，下一级向上同步，同步子网可动态重配置。这与数据中心里"园区一套权威源 + PTP 逐级分发"的结构同构。
- **三种同步模式**【考点】：**组播模式**（高速 LAN 内广播，效率高精度低）、**client/server 模式**（同 Cristian，精度中等）、**对称模式**（一对服务器互发保留时序信息，精度最高）。
- **偏移估计公式**【考点】：A、B 互发消息，记 4 个时间戳 Ti-1（A 发）、Ti-2（B 收）、Ti-3（B 发）、Ti（A 收）。设去程回程相等（t = t'），则 B 相对 A 的偏移估计 **oi = [(Ti-2 − Ti-1) + (Ti-3 − Ti)] / 2**，总延迟估计 **di = (Ti-2 − Ti-1) + (Ti − Ti-3)**。延迟越小的样本越可信。
- 工程延伸（课件新增）：Spanner **TrueTime** 不假装时钟准，而是把误差 ε 显式暴露（TT.now() 返回 [t−ε, t+ε] 区间，ε≈1–7ms 锯齿状），事务取时间戳后 **commit-wait 2ε** 再提交，换来外部一致性；CockroachDB 不买硬件，把 ε 放宽到 500ms，读到落在不确定区的写就重启事务——**同一个不确定性，硬件 vs 重试两种权衡**。

### 3.5 逻辑时间、逻辑时钟【考点】

物理时钟既然永远有误差，能不能干脆绕开它？Lamport 1978 年的回答是：**可以，因为很多应用根本不需要知道物理时间，只需要所有机器对"谁先发生"有一致的看法**。他给出的关键论断：**不进行交互的两个进程之间不需要时钟同步**——互不交互的进程各自时间走得再乱，谁也察觉不到，更不会出问题。需要一致的只是：**所有进程对事件的发生顺序达成一致**。事件排序是互斥算法、死锁检测等众多分布式算法的基石。

### 3.6 发生在先关系、并发关系【考点】

**happens-before（→）关系**是逻辑时序的基石，由三条规则定义（是**偏序**，不是所有事件都可比较）：
1. 同一进程内：若事件 e 在 e' 之前（e →i e'），则 e → e'；
2. 消息规则：对任意消息 m，send(m) → recv(m)；
3. 传递性：e → e' 且 e' → e''，则 e → e''。

这两条规则背后是两个物理事实：同一进程的先后是确定的；消息的发送必然先于接收。

**并发关系**【考点】：e ∥ e' ⟺ e→e' 与 e'→e 都不成立。**并发 ≠ 同时发生**，它只是说"这两个事件之间没有因果链，谁也不依赖谁"。

例（课件 p29）：p1 的事件 a、b，p2 的 c、d，p3 的 e、f。由消息可得 b→c、d→f，传递出 b→d、b→f、c→f；而 b 和 e 之间没有任何消息链，不可比较，即 b ∥ e。

### 3.7 Lamport 时钟、全序逻辑时钟【考点】

**机制**：每个进程维护一个单调递增的软件计数器 Li 充当逻辑时钟，规则只有两条：
- **LC1**：进程 pi 执行任何事件（含发送）前，Li := Li + 1；
- **LC2**：pi 发消息 m 时附带时间戳 t = Li；pj 收到 (m, t) 时，先 **Lj := max(Lj, t)**，再执行一次 LC1——即接收事件的时间戳为 max(Lj, t) + 1。

直觉：收到消息说明"对方那边至少已经走到了 t"，所以自己至少要走到 t+1，保证"发送 → 接收"映射成"小时间戳 → 大时间戳"。

**必须记住的性质（判断题重灾区）**【考点】：
- **e → e' ⇒ L(e) < L(e')**（成立，可证明：沿因果链每一步时间戳严格增大）；
- **L(e) < L(e') ⇏ e → e'**（反向不成立！Lamport 时钟**不捕获因果**——两个并发事件完全可能撞出 Lamport 时钟的大小关系，但它们之间没有因果）。
- 不同进程可能产生**相同**的 Lamport 时间戳（各自独立 +1）。

**全序逻辑时钟**：为了给所有事件排出唯一的全序，把进程标识符拼进时间戳——事件 e（进程 pi）的全局时间戳为 (Ti, i)，比较规则 e < e' ⟺ Ti < Tj 或 (Ti = Tj 且 i < j)。**没有物理意义**（纯粹的人为约定），但有用：系统中所有事件的时间戳两两不同，互斥等算法需要全序来"破对称"。

### 3.8 向量时钟【考点】

**为什么不够**：Lamport 时钟只保证"因果 ⇒ 时间戳小"，但看到两个时间戳一比大小，你**无法判断**是真因果还是并发——它没有区分"来源"。向量时钟补上这一点：让每个进程不仅数自己，还记录"我见过的其他每个进程走到了哪"。

**规则**（每进程维护向量 Vi[1..N]）：
- **VC1**：初始 Vi[j] = 0；
- **VC2**：pi 给事件加时间戳前，Vi[i] := Vi[i] + 1；
- **VC3**：pi 发消息时附带 t = Vi（整个向量）；
- **VC4**：pj 收到消息中的 t 时，对**每个**分量取 max：Vi[j] := max(Vi[j], t[j])，称为**合并**。

与 Lamport 时钟的记忆对比：**Lamport 是"max + 1"，向量时钟是"逐分量 max，然后只给自己的分量 +1"**（VC2 在加戳前执行）。

**大小关系**（考试计算的基础）：V1 = V2（逐分量相等）；V1 ≤ V2（逐分量 ≤）；V1 < V2（≤ 且 ≠）；**V1 ∥ V2（互不 ≤，即至少存在 i、j 使 V1[i] > V2[i] 且 V2[j] > V1[j]）**。

**核心定理（向量时钟的全部意义）**【考点】：
- e → e' ⟺ **V(e) < V(e')**
- e ∥ e' ⟺ V(e) ∥ V(e')
- e = e' ⟺ V(e) = V(e')

物理意义：向量时钟的第 j 个分量 = 该事件所观察到的"进程 pj 已经走到哪"。它携带全局信息，而 Lamport 时钟只有局部计数。

**工程应用**（课件重点，帮助理解也贴近面试）：
- Raft 的 term ≈ 一个 Lamport 时钟（本地选举时 +1，RPC 携带，见大取 max）；Kafka 的 offset 是分区内全序、整体偏序；Git 的提交图——commit 父子关系就是 happens-before，两个分支是并发 ∥，merge 是合并两条历史。
- **Dynamo**：每个对象版本带向量时钟；读到 V1 < V2 直接丢旧版，读到 V1 ∥ V2 返回 siblings 让应用合并（购物车取并集）。代价：向量随节点数增长必须截断，截断后可能把因果误判成并发（宁可多报并发不可漏报）。对照 Cassandra 用物理时间戳 last-write-wins：实现简单但钟不准时会**静默丢数据**——向量时钟的代价是元数据体积，LWW 的代价是对时钟的信任。
- CRDT 协同编辑（Yjs/Automerge）：因果就绪检查（操作必须等其依赖到齐才能应用）就是 happens-before 的直接工程化；V1 ∥ V2 时用可交换的合并规则自动收敛。
- **HLC 混合逻辑时钟**：时间戳（物理部分 l，逻辑部分 c），既保持因果（e→e' ⇒ HLC 递增）又贴近物理时间（能回答"十分钟前的状态"），且定长不随节点数 O(N) 膨胀——这就是向量时钟不适合几千节点系统的原因，也是 CockroachDB 的选型。

### 3.9 割集、割集的一致性、一致的全局状态【考点】

**动机**：很多事必须看"全系统此刻的状态"才能判断——分布式垃圾收集（引用计数要包含信道里的消息）、分布式死锁检测（等待图有没有环）、终止检测、调试。但分布式系统没有"此刻"——各机器时间不同步，怎么可能拍一张全员合影？

- **割集（cut）C**：给每个进程的历史各取一个前缀，这些前缀的并集。直观上就是在时空图上画一条竖向的锯齿线，线左边就是"拍到的快照"。
- **一致割集**【考点】：满足——**对任何事件，若 e' 在割集内且 e → e'，则 e 也在割集内**。物理含义：快照不能出现"收到了一条还没有被发送的消息"——那是一个不可能出现过的系统状态（钱凭空多出来了）。一致割集对应的状态虽然未必来自同一物理时刻，但它是**一个可能发生过的、合理的现实**。
- **一致的全局状态**：一致割集对应的全局状态。
- **走向（run）**：S0 → S1 → S2 → …，系统的一种可能执行过程。
- **线性化走向（consistent run）**：只经历一致全局状态的走向。
- **可达**：若存在一个经过 S 和 S' 的线性化走向，则称 S' 从 S 可达。

### 3.10 Chandy-Lamport 快照算法【考点】

**要解决的问题**：在不停机、不打断正常执行的前提下，拍下一张一致的全局状态"照片"。难点：消息在网线上飞着，光记各进程状态不够——**通道（在途消息）也是状态的一部分**。

**假设**（缺一不可，判断题爱考）：进程和通道不出故障；通道**单向、FIFO**；进程间强连通；任一进程可随时发起；拍照期间进程照常执行和收发消息。

**算法只靠一种特殊消息——marker（标记），两条规则**：

- **标记发送规则**【考点】：进程 pi 记录完自己的状态之后、**沿通道 c 发送任何其他消息之前**，先在 c 上发送一个 marker（对每条外出通道都发）。
- **标记接收规则**【考点】：pi 在通道 c 上收到 marker 时：
  - 若 pi **还没记录过**自己的状态：立即记录自己的状态；把 **c 的状态记为空集**（说明 c 上在拍照点之后没有在途消息——FIFO 保证 marker 之前的消息都已收到）；并**开始记录其他接入通道**上到达的消息（这些通道的 marker 还没来，消息可能在途）；
  - 若 pi **已记录过**：把从记录状态以来在 c 上收到的消息集合记为 **c 的状态**（这就是被"夹"在途中的消息）。

**执行过程三段**：发起者记录自身状态并向所有外出通道发 marker（N−1 条）→ marker 沿图传播，各进程按接收规则处理 → 终止条件：每个进程在**全部 N−1 条输入通道**上都收到了 marker；之后可由中央进程汇总拼出全局快照。

**为什么是一致的（正确性论证思路）**：设 ei → ej 且 ej 被 pj 记录，反证 ei 没被 pi 记录——则 ei 发生在 pi 发 marker 之后，由 FIFO，链路上的每个 recv(mi) 都发生在对应进程收到 marker 之后，一路推下去 ej 也必须发生在 marker 之后，就不会被记录，矛盾。

**经典例子（要会讲）**：p1、p2 做交易，每件 $10。初始 p1:⟨$1000, 0 件⟩、p2:⟨$50, 2000 件⟩；之后 p1 买 10 件（$100 订单在途）、p2 发 5 件货（5 件在途）。快照拍到：p1:⟨$900, 0⟩、p2:⟨$50, 1995⟩、c12:⟨订单 10 件 $100⟩、c21:⟨5 件货⟩。这个状态**从未在任一物理时刻真实存在过**，但金额+货物守恒、完全自洽——正是一致快照的意义：**它等价于系统在某个逻辑时刻的状态**。

**工程闭环（课件重点）**：Flink checkpoint 是 C-L 的变体——marker 对应 checkpoint barrier。对齐 checkpoint 允许阻塞先到 barrier 的通道（排空在途数据），因此**不用记录通道状态**，快照小；代价是反压时对齐可能超时。Flink 1.11 起的非对齐 checkpoint 让 barrier 插队并把队列里的在途数据一并写入快照——**这就是 C-L 的完整形式（进程状态 + 通道状态）**。对比记忆：C-L 不允许阻塞（通用拓扑可能有环，阻塞会死锁），所以必须记通道；Flink 靠 DAG 假设换来了简化。

### 3.11 分布式调试（全局状态谓词的判断）【考点】

有了快照能力，就能回答"系统是否曾处于某种状态"——例如安全条件 |xi − xj| ≤ δ 是否满足、所有阀门是否曾同时开启。

- **全局状态谓词** Φ：从全局状态集合到 {True, False} 的映射。
- **稳定谓词**：一旦在某状态为 True，之后所有可达状态恒为 True——如"系统死锁""系统终止"。稳定谓词只需观察到一次 True 即可下结论，这就是快照的价值。
- **安全性 safety**："坏事情永不发生"——对所有可达状态 Φ 均为 False（死锁自由、无孤儿对象、共识中不出现两个不同决定值）。违反可以**有限步骤内确认**（找到一个坏状态即可）。
- **活性 liveness**："好事情终将发生"——任何线性化走向最终到达 Φ 为 True 的状态（无饥饿、最终一致、共识最终决定）。违反**无法有限步骤确认**（好事情可能"随后"就发生）。
- **判定方法**：监控器收集带向量时钟的状态，先按 **CGS 条件**确认一致性——全局状态 S = (s1,…,sN) 一致 ⟺ **V(si)[i] ≥ V(sj)[i] 对所有 i, j 成立**（直觉：si 里"对自己进程"的计数必须是全场最大，否则说明 si 依赖了别人还没发生的状态，割集不一致）。然后在**一致全局状态网格（lattice）**上判定：
  - **可能 Possibly Φ**【考点】：存在**一个**一致全局状态使 Φ 为 True（网格里找到一个 T 即可）；
  - **明确 Definitely Φ**【考点】：**所有**线性化走向都经过使 Φ 为 True 的状态（只要有一条从初始到终止全为 F 的路径，就不是 definite）。
- 工程对应：OpenTelemetry/Jaeger 分布式追踪（span 父子关系 = 因果边）、Jepsen Elle（从读写历史重建依赖图找环 = 死锁检测同思路）、FoundationDB 确定性模拟（把整个集群跑在单线程模拟器里，一个随机种子可完整重放）、TLA+（Lamport 自己发的形式化验证工具，AWS/MongoDB 用于验证协议的 safety/liveness）。

## 第 4 章 协调和协定

> 本章主线：分布式系统里的进程要协作，就要解决四类协调问题——互斥（谁能用资源）、选举（谁说了算）、组播（消息怎么可靠且有序地发给一群人）、协定（大家对一个值达成一致——共识）。

### 4.0 故障检测器（铺垫）

不可靠故障检测器的实现：每个进程周期 T 通告"我还活着"；检测器以 D 为最大传输延迟，超过 T+D 没收到就把该进程标为 Suspected。T、D 可动态调。**可靠的故障检测器不存在**——异步系统里超时只能说明"怀疑"，不能证明崩溃（呼应第 2 章同步/异步之分）。

### 4.1 分布式互斥【考点】

**要解决的问题**：在没有共享内存的系统中，仅靠消息传递，保证对共享资源一次只有一个进程访问。接口：enter()（必要时阻塞）/ resourceAccesses() / exit()。假设：异步系统、无故障进程、可靠投递。

**三个基本要求**【考点】：
- **安全性**：临界区内最多一个进程；
- **活性**：enter/exit 最终成功（无死锁、无饥饿）；
- **顺序**：进入次序与请求的 happen-before 次序一致（强信号量语义）。

**四个性能指标**：带宽（enter/exit 各发几条消息）、客户延迟（从请求到进入/退出的等待）、吞吐率、**同步延迟**（一个进程退出到下一个进程进入的间隔——衡量切换速度）。

**方法一：中央服务器算法**。所有请求发给持有令牌的服务器（request / grant / release 排队）。满足安全与活性，**不满足顺序**（异步系统中消息到达次序不定）。性能：enter 2 条消息（请求+授权）、exit 1 条；同步延迟 = 2 条消息（release + grant）。致命伤：**单点故障 + 性能瓶颈**。

**方法二：基于环（令牌环）**。进程组成逻辑环，令牌沿环传递；拿到令牌的进程想进就进，不想进立即传给下一个。满足安全与活性，不满足顺序。性能：即使没人进临界区，令牌也在转——**带宽持续消耗**；enter 延迟 0～N 条消息（看令牌离你多远）；同步延迟 1～N 条。环断了则失效。

**方法三：组播 + 逻辑时钟（Ricart & Agrawala）**【考点】。思路："进临界区需要全票同意"——
- 进入：置 WANTED，组播 request（带 Lamport 时间戳 T），收齐 **N−1 个应答**后进入；
- 进程 pj 收到 request ⟨Ti, pi⟩ 时：若自己 HELD，或自己也是 WANTED 且 (Tj, j) < (Ti, i)（自己的请求"更优先"），则**把请求排队不回**；否则立即应答；
- 退出：置 RELEASED，并回复所有排队的请求。

为什么正确：两进程并发请求时，全序比较 (T, pid) 保证了**恰有一方更优先**——更优先者会收到所有应答进入；另一方会推迟应答，直到对方退出。Lamport 时间戳在这里的作用就是**破对称防死锁**（否则互相等对方让步）。满足全部三个要求（顺序：全序包含 happen-before；安全性/活性用反证法）。

性能【考点】：enter 发 **2(N−1)** 条消息（N−1 请求 + N−1 应答）；客户延迟一次组播往返；**同步延迟仅 1 条消息的传输时间**（退出者直接应答下一个等待者，不经服务器）——三者中最快，代价是消息数最多。

**方法四：Maekawa 投票算法**【考点】。组播法消息太多（人人都要问全员），Maekawa 的观察：**不必问所有人，只要"投票集"设计得当**。每个进程 pi 有一个大小为 K 的投票集 Vi（经典构造：√N×√N 网格取行与列，使任意两个投票集**恰交于一个进程**）；进入临界区只需收齐 Vi 中 **K 票**；任何进程一次只能投一票（voted 标志），HELD 或 voted=TRUE 时把请求排队；退出时组播 release，收到 release 的进程从队列头取下一个请求补投。

优点：消息量 **O(√N)**，远小于 2(N−1)。**缺陷：会死锁**【考点】——经典反例：p1、p2、p3，V1={p1,p2}，V2={p2,p3}，V3={p3,p1}；三个进程并发请求，各自先给"自己"投了票（各 voted=TRUE），然后互等对方那一票，循环等待。补救：给请求加优先级/时间戳，或超时放弃重试。

### 4.2 分布式选举【考点】

**含义**：选出一个唯一进程担任特殊角色（协调者），通常约定选**标识符最大的存活进程**。术语：召集选举（发起一次运行）、参与者、非参与者；进程标识符唯一且可全序排列。

要求：安全性（electedi 为空或恰为最大存活 pid）；活性（所有进程最终得到结果，或自身崩溃）。性能：带宽（消息总数）、周转时间（串行消息传输次数）。

**方法一：基于环的选举**。按逻辑环传递 {elect, id} 消息：
- 发起者标记自己为 participant，发自己的 id；
- 收到 elect：若来的 id 比自己大 → 标记 participant 并转发；若比自己小且自己是 non-participant → 换成自己的 id 转发（自己是参与者则什么都不做）；若相等 → 自己就是最大者，改发 {elected, id}；
- elected 消息绕环一圈回到发起者（即当选者）时结束。

性能【考点】：最坏 **3(N−1)** 条消息（发起者的逆时针邻居恰好是最大 id）；最好周转 2N。**不具备容错**——环断了整个算法失效。

**方法二：霸道（Bully）算法**。适用**同步系统**（用超时检测崩溃），通道可靠但进程可崩溃；每个进程知道谁 id 更大、且可与所有人直接通信。流程【考点】：
- P 发现协调者故障 → 向所有**更大 id** 的进程发 election；
- 无人应答 → P 自己就是最大存活者，向所有更小 id 进程发 coordinator；
- 有应答（哪怕一个）→ 说明有更大的活着，P 等 coordinator；等待超时（更大的临时崩了）→ P 重新发起选举；
- 大 id 进程收到 election：回 answer（让小 id 等着），并自己再发起一轮选举；
- 所有进程收到 coordinator：设置 electedi。

"霸道"的名字来源：id 最大的进程一旦恢复/存在，**必然**夺回协调者位置，哪怕现任干得好。性能【考点】：最好 **N−2** 条消息（次大者发起，直接宣布）；最坏 **O(N²)**（最小者发起，每一层大 id 依次接手又崩溃，触发 N−2 次选举、每次 O(N) 条）。

### 4.3 组播通信【考点】

**问题**：把一条消息发给一组进程（组播）或全体（广播），要同时管三件事：效率（带宽/时间）、投递保证（可靠性 + 顺序）、组成员管理（任意加入退出）。封闭组：只有组员能向组发；开放组：组外也能发。

**第一层：基本组播 B-multicast**。实现就是"给每个成员逐个 send"，成员收到后 B-deliver。保证：只要组播者不崩溃，正确进程最终投递。**缺陷：不保证协定**——发送者中途崩溃，就可能一部分人收到、另一部分没收到。

**第二层：可靠组播 R-multicast**【考点】，三个性质（必背）：
- **完整性 Integrity**：正确进程对每条消息**至多投递一次**（不重、不伪造）；
- **有效性 Validity**：正确进程组播的消息，**它自己**终将投递；
- **协定 Agreement**：一个正确进程投递了 m，则组内**其他**正确进程终将投递 m。

与 B-multicast 的本质区别：R-multicast 的结果是"**要么全部投递，要么全不投递**"，即使 sender 中途崩溃。

**实现一：基于 B-multicast 的洪泛算法**【考点】：发送者对全组 B-multicast；任何进程 q 第一次 B-deliver 到 m 时（用 Received 集合判重），**自己也再 B-multicast 一次给全组**，然后 R-deliver。直观：一条消息被 q 收到后就"扎根"了——就算原发送者崩溃，q 会替它继续传。满足三性质；代价：每条消息每个进程会收到 |g| 次，总消息数 **|g|²**——正确但效率低。

**实现二：基于 IP 组播 + 捎带确认 + 否认确认**：
- 每进程维护 Sg,p（自己下一个发送序号）和 Rg,q（来自 q 的最新序号）；
- 发送时在消息里**捎带**自己对别人的最新序号（piggyback 确认）；接收方检查：m.S = Rg,p + 1 → 正好连续，投递；m.S ≤ Rg,p → 重复，丢弃；m.S > Rg,p+1 或捎带的 Rq 表明有缺失 → 把消息放进**保留队列 hold-back queue**，发 **NACK** 索要缺的消息。
- 保留队列不是可靠性的必需品，但它用序号刻画"已投递集合"，提供了投递顺序保证。
- 局限：协定性质需要"进程无限组播 + 无限保留消息"才严格成立，不现实；派生协议（如 Psync 周期同步清史）来补。

**统一性质（Uniform）**【考点】：更强的保证——**连故障进程也纳入约束**。统一协定：**任何**进程（无论后来是否崩溃）只要投递了 m，组内所有正确进程终将投递 m。实现技巧就在洪泛算法的**两行次序**：把"再组播给全组"放在 "R-deliver" **之前**就满足统一协定（先扎根再自用）；交换两行则一个进程可能 deliver 后立即崩溃，无人替它传播，统一协定即被破坏。

**有序组播**【考点】——可靠性之上，还要约定"投递次序"：
- **FIFO 排序**：同一发送者先发的先投（各发送者独立序号即可实现，同上文的序号+保留队列方案）。
- **因果排序**：若 multicast(m) → multicast(m')（有因果链），则任何进程先投 m 后投 m'。实现用**向量时钟**：CO-deliver 的条件是"pj 更早的消息已投 + pj 组播该消息时已见过的消息都已投"，不满足就压在保留队列。与 FIFO 的区别：FIFO 只看单发送者，因果序**跨进程**（C1→C3 因果相关，C2∥C3 并发）。
- **全排序**：所有正确进程**以完全相同的次序**投递所有消息（不关心这个次序是什么，只要求一致）。两种实现：
  - **Sequencer（定序器）**：一个专门节点给消息分配连续序号并广播，大家按号投递——简单，但定序器是单点。
  - **ISIS 算法**（去中心）：发送者 B-multicast 消息；每个接收者提议一个序号（Pg,q = max(Ag,q, Pg,q) + 1）回给发送者；发送者取**最大提议值 a** 作为协定序号广播；各进程按 a 在保留队列里重排后投递。可能的冲突（两个消息被提了同一个号）用进程 id 破对称：⟨proposal⟩.⟨pid⟩。分析：正确进程最终对同一组序号达成一致、序号单调；**不保证**因果/FIFO 序；延迟比定序器方案更大。

### 4.4 共识、交互一致性与拜占庭将军问题【考点】

**共识问题**：一个或多个进程提议值，最终**所有进程对同一个值**达成一致。形式化：pi 有提议值 vi 和决定值 di。三个要求【考点】：
- **终止性**：每个正确进程最终设置决定变量；
- **协定性**：正确进程的决定值相同（di = dj）；
- **完整性/有效性**：若所有正确进程提议同一个值 v，决定值必须是 v。

朴素算法：每个进程可靠组播自己的提议 → 收集全员提议 → 取 majority()（抽象函数，可为 max/min/多数）。终止性靠组播可靠性，协定性/完整性由 majority 定义保证。

**FLP 不可能原理**【考点】：Fischer–Lynch–Patterson（1985）证明——在网络可靠但允许哪怕**一个**节点失效的**异步**系统中，**不存在**能保证终止的确定性共识算法。根源还是那个问题：异步系统里无法区分"慢"和"死"。实践含义：异步环境下的共识算法（Paxos/Raft）都只保证 safety 无条件成立，liveness 在"足够多的进程正常、通信最终恢复"的弱假设下成立。

**拜占庭将军问题（BGP）**：共识的"恶意版"。司令发布命令，中尉执行；**一个或多个将军可能叛变**（任意行为：不发、乱发、对不同人发不同命令）。要求：
- 终止性（同上）；
- **协定性**：所有**正确**进程的决定值相同（叛徒说什么无所谓）；
- **完整性**：若**司令**正确，所有正确进程采用司令的值。

与共识的区别【考点】：共识是"多来源取一个"，BGP 是"**单一来源**（司令）提供值，其余人决定是否采用"。还有第三个变体**交互一致性 IC**：每个进程都提议一个值，大家就一个**向量**达成一致，完整性要求"pi 正确则向量第 i 分量 = vi"。

**三者互相归约**（考点：会用一种算法解另两种）：
- BG → IC：把 BG 算法跑 N 次，每次轮流让 pj 当司令：ICi(…)[j] = BGi(j, vj)。
- IC → 共识：对决定向量取 majority。
- 共识 → BG：司令把值 v 发给自己和所有人，然后所有人拿收到的那组值跑共识算法。

**同步系统 + 崩溃故障的共识**：N 进程至多 f 个崩溃。算法跑 **f+1 轮**：每轮把"自己还没广播过的值"B-multicast 出去，超时收值并入集合；f+1 轮后 d = min(Values)。为什么是 f+1 轮【考点】：最坏情况每轮恰好崩一个进程，且它崩前只把值传给一个人——这个值每轮只前进一跳，需要 f+1 轮才能让所有正确进程都看到；而 f+1 轮里至少最后一轮无人崩溃，B-multicast 保证大家看到相同集合 → 协定性成立。

**三个拜占庭将军（N ≤ 3f 无解）**【考点】——这是本章最容易出分析题的点：
- 两个场景对比：场景一，司令 p1 正确发 v，p3 叛变对 p2 说 "u"；场景二，司令 p1 叛变，对 p2 发 w、对 p3 发 x。p2 收到的信息**在两个场景里完全一样**，无法分辨司令是好人还是叛徒。
- 若存在算法：场景一中完整性迫使 p2 选 v（司令正确）；那么场景二中 p2 也不得不选 w（同样的输入）。由对称性，p3 在场景二选 x → p2 ≠ p3，违反协定性。**所以 3 个进程、1 个叛徒，无解**（除非对消息加**数字签名**——签名让司令无法抵赖/伪造，改变信息结构）。
- 推广到 N ≤ 3f：把 N 个将军分成 3 组 n1+n2+n3 = N（每组 ≤ N/3），让 p1、p2、p3 分别**模仿**一组——3 进程无解 ⇒ N ≤ 3f 也无解。
- **为什么下界是 3f+1**（直观推导）：f 个坏进程可能干脆不发消息，要定结果得靠 N−f 个消息；但你无法区分这 N−f 里混了几个坏消息，最坏有 f 个，剩下的好消息必须**多于**坏消息：N − f − f > f，即 **N > 3f**。

**四个拜占庭将军（N = 4, f = 1）**【考点】——正确方案长什么样：两轮消息 + majority：
- 第一轮：司令给每个将军发一个值；
- 第二轮：每个将军把自己收到的值转发给其他所有人；
- 最后每个将军对自己收到的（司令值 + 3 个转发值）执行 majority。
- 司令正确时：p2 = majority(v, u, v) = v，p4 = majority(v, v, w) = v——一致且等于司令值；
- 司令叛变时（发 w/u/v/x）：p2 = p3 = p4 = majority(u, v, w) = ∅（默认值）——虽然不等于司令值，但**协定性**（大家一致）成立，完整性只对"司令正确"有要求，所以仍然正确。

**Lamport OM(m) 算法**【考点】：定理——将军数 **> 3m**（即 3m+1）且叛徒 ≤ m 时，递归算法 OM(m) 达成共识。上面 N=4 的两轮 majority 就是 OM(1)。代价【考点】：**f+1 轮**消息、**O(N^(f+1))** 条消息；Fischer–Lynch（1982）证明 f+1 轮是拜占庭容错的下界——任何确定性算法都逃不掉。应用：核电站、Bitcoin、Boeing 777、SpaceX Dragon 这类"故障不可信"场景。异步环境 + 拜占庭受 FLP 约束，需要弱同步假设（PBFT）或 N 版本编程。

**PBFT（实用拜占庭容错）**【考点】：3f+1 个副本容忍 f 个拜占庭节点。正常流程五步：
1. 客户端把请求发给 primary；
2. **pre-prepare**：primary 打包提案（含序号 n、视图 v）签名广播给所有副本；
3. **prepare**：副本验证通过后广播 prepare；收集到 **pre-prepare + 2f 个匹配的 prepare** 即进入 prepared 状态（第一轮投票）；
4. **commit**：prepared 的副本广播 commit；收集 **2f+1** 个匹配 commit 后执行并回复（第二轮投票）；
5. 客户端收到 **f+1** 个相同 reply 才接受结果。

数量关系要理解：quorum 取 2f+1 是因为任意两个 2f+1 的集合**至少交于一个正确副本**，这是安全性的根；而 reply 只要 f+1，因为执行前安全性已由前两阶段锁死，客户端只需保证至少一个回复来自正确副本。primary 坏了 → **view change**（超时触发，新 primary = v mod |R|）。局限：消息数 O(n²)，比崩溃容错贵一个量级。

**Paxos（崩溃容错 CFT 共识）**【考点】：
- 假设：部分同步（甚至异步）、消息可丢失/重复/延迟/乱序（损坏可检测）、**只有崩溃故障**（重启可恢复）、不共谋。
- 角色：**Proposer**（收到客户请求，发起提案；提案 = 唯一编号 + 值）、**Acceptor**（记住协议状态；**quorum = 任意多数派**）、**Learner**（得知决议，执行请求/回复客户）。
- Safety 三条：只有被提出的值才能被选中；只选中唯一一个值；节点不会"学到"一个没真正被选中的值。
- **两阶段流程**（必背，要能写出四类消息）：
  - **Phase 1a Prepare**：Proposer 选编号 N，向一个 quorum 发 prepare(N)；
  - **Phase 1b Promise**：Acceptor 若 N 大于它**曾 promise 过和 accept 过**的所有编号，则承诺"永不接受编号 < N 的提案"，回 promise(N, (n, U))，U 是它已接受的最高编号提案（没有则为空）；
  - **Phase 2a Accept**：Proposer 收齐 quorum 的 promise 后发 accept(N, W)，其中 **W = promise 里最高编号提案的值；若所有 promise 都没带提案，W 才可以任取自己的值**（这一条保证了已选出的值不会被翻盘）；
  - **Phase 2b Accepted**：Acceptor 若 N ≥ 它之前 promise 的编号，就接受提案（写稳定存储）并通知。
- 失败重试：提案 N 可能因"有更新编号的 promise 压制"或"凑不齐 quorum"而失败，换更大编号重来；多个 Proposer 互相压制 → **dueling proposers 活锁**，Multi-Paxos 用稳定的 leader 解决。
- **容忍 f 个故障需要 2f+1 个 acceptor**【考点】（课件原题：多数派相交）。

**Raft**（Paxos 的可理解等价物）【考点】：
- 基座：**复制状态机**——每节点跑相同的确定性状态机，从相同初始状态出发，执行相同命令序列（复制日志）必达相同终态；共识模块的任务就是保证日志一致。
- **三种状态**：Leader（处理一切客户交互与日志复制）/ Follower（完全被动）/ Candidate（选举用）。启动全是 Follower；Leader 周期发心跳（空 AppendEntries）；**选举超时 100–500ms** 没听到心跳就认为 Leader 崩了，发起选举。
- **任期 term**：单调递增的逻辑时钟——本课第 3 章"逻辑时钟"的现役实现（本地发起选举时 term++，每条 RPC 带 term，见大即更新/退位）。term 的核心价值是**识别过期信息**：任何 RPC 里发送方 term 小就拒绝，接收方 term 小就转 Follower。
- **选举**：Candidate 给自己投票、向所有人发 RequestVote；获**多数票**成为 Leader 并立刻发心跳；收到有效 Leader 的 RPC 则退回 Follower；超时无人获胜则 term++ 重选。安全性：**每人在每任期只投一票（持久化到磁盘）** ⇒ 每任期至多一个 Leader。活性：各服务器在 **[T, 2T] 中随机选选举超时**（T ≫ 网络 RTT），先醒者先选先赢，避免选票瓜分。
- **日志复制**：日志条目 = ⟨index, term, command⟩，先写稳定存储；Leader 收到命令 → 追加到本地日志 → 并行发 AppendEntries → **多数派存下即提交** → Leader 执行并把结果回客户 → 跟随者随后各自执行。跟随者崩溃/慢：Leader 无限重试。一致性检查：AppendEntries 携带前一条目的 index+term，跟随者对不上就拒绝。
- **安全性**（要能讲出"为什么需要这两条"）：
  - Leader 永不覆盖自己日志；只有 Leader 的条目可被提交；
  - **选举限制**：RequestVote 携带候选者最后条目的 (term, index)；投票者发现候选者日志"不如自己新"（term 小，或同 term 但 index 小）就拒绝 ⇒ 当选 Leader 必然拥有所有已提交条目，否则已提交数据可能被覆盖（课件 S5 场景：旧任期条目可能因此无法安全提交）；
  - **提交规则**：Leader 只直接提交**当前任期**的条目；提交它会连带提交之前所有条目。
- **修复跟随者日志**：Leader 为每个 follower 维护 nextIndex（初始为自己的最后 index+1），AppendEntries 一致性检查失败就 nextIndex-- 重试，最终删掉 follower 多余条目、补齐缺失条目。
- **平衡旧 Leader**：旧 Leader 掉线又回来，靠 term 识别——任何 RPC 一比较 term 就知道谁是过期的；被废黜者无法提交新条目。
- **客户端协议**：不知道 Leader 就随便连一台（会重定向）；Leader **提交并执行后**才响应；请求超时客户端就重发，靠**唯一请求 ID**（写入日志，接受前查重）实现 exactly-once 语义。
- **配置变更**：不能直接从旧配置切到新配置（新旧配置可能各自选出多数派、做出冲突决定）→ **联合共识**：过渡配置 Cold,new 需要新旧**两个**多数派同时同意才提交；提交后才切换到 Cnew。

## 第 5 章 事务和并发控制

> 本章主线：多个事务并发访问同一批对象，会出现"更新丢失""不一致检索"两类错误。判别正确性的标尺是**串行等价**；实现它的三条技术路线是**锁（悲观等待）**、**乐观（先干后验）**、**时间戳排序（按既定次序裁决）**。

### 5.1 事务与 ACID【考点】

**事务**：客户定义的、针对服务器对象的一组操作，作为一个**不可分割的单元**由服务器执行。目标：无论并发还是故障，服务器管理的对象始终保持一致状态。

事务能处理的故障模型：进程崩溃 + 通信遗漏故障；**不能处理拜占庭行为**。

**ACID**【考点】（每个字母要能解释 + 说出实现手段）：
- **Atomicity 原子性**：全有或全无——事务要么全部效果生效，要么像没发生过。放弃（abort）时回滚（rollback）写入。实现：预写式日志（undo）；分布式事务用两阶段提交。
- **Consistency 一致性**：事务把数据库从一个一致状态（满足完整性约束，如借贷总额相等）搬到另一个一致状态。注意这是**应用层面**的属性，依赖应用怎么用数据库——**与 CAP 理论的 C 不是一回事**（CAP 的 C 指多副本间每次读能读到最近的写，是操作层面的强一致）。
- **Isolation 隔离性**：事务执行中的中间效果对其他事务不可见——每个事务仿佛独占整个数据库。实现：两阶段加锁/乐观并发控制/时间戳排序（本章全部内容）。
- **Durability 持久性**：一旦提交，效果永久保存。实现：预写式日志（redo）+ 存储管理（早期靠磁带/硬盘，现代靠复制）。

事务的三种结局：成功提交；客户主动放弃；服务器放弃（死锁解除、验证失败等）并向客户报 ERROR。一旦放弃，服务器必须清除全部效果，使其对其他事务不可见。

### 5.2 并发事务的两个典型问题

用银行例子（记住数字便于复述）：A、B、C 初值 $100、$200、$300。

- **更新丢失**：T 做转账 A→B（B 增 10%），U 做转账 C→B（B 增 10%）。若两人**同时读**到 B=$200，各自算出 220 写回——两次增幅只剩一次，B 应为 242 却成了 220。根因：**读旧值算新值再写回**，后写覆盖先写。
- **不一致检索**：V 转账（A 取 100、B 存 100），W 同时算 branchTotal。W 在 V"已取款、未存款"的中间态读账 → 总额少 100。根因：**读到了别的事务的中间状态**。

### 5.3 串行等价性的概念、充要条件及应用【考点】

**定义**：并发事务交错执行的效果，若等同于"按**某种次序**一次执行一个事务"的效果，则该交错是**串行等价的**。以它为标准可同时防止上述两个问题——串行执行根本不会有交错问题。

**冲突操作**：两个操作若"效果与执行次序有关"就互为冲突。冲突表（不同事务、同一对象）：
- read–read：**不冲突**（先后读结果一样）；
- read–write：**冲突**（先写后读读到新值，先读后写读到旧值）；
- write–write：**冲突**（终值取决于谁后写）。

**充要条件**【考点】（本章核心，判断与构造交错全靠它）：**两事务串行等价 ⟺ 两者所有的冲突操作对，都以相同次序在对象上执行**。

应用方法论（会做题的关键）：对每一对冲突操作，标记它是"先 T 后 U"还是"先 U 后 T"；**所有标记一致** → 串行等价（且等价于那个方向）；**出现相反标记** → 非串行等价。"效果相同"的定义：读操作返回值相同 + 对象最终状态相同。

### 5.4 事务放弃时的恢复

串行等价只管"都成功"的情形；有事务**放弃**时还有两个坑：

- **脏读**：U 读到了未提交事务 T 写的值，之后 T 放弃——但 U 若已提交就无法取消，等于一个从未存在过的值影响了数据库。对策：**可恢复性**——U 推迟提交，直到它读过的事务都已提交。连锁反应：T 放弃可能逼着一串读过它数据的事务连环放弃（**连锁放弃**）；根治：**只允许读已提交事务写的数据**。
- **过早写入**：回滚按"前映像"恢复，若两个事务先后写了同一对象，先提交者放弃时把后提交者的值覆盖回旧值（T 写 105、U 写 110；U 提交、T 放弃 → 恢复成 100，错）。对策：**write 必须等之前写同一对象的事务提交或放弃后才能执行**。
- **严格执行**：干脆 read 和 write 都推迟到写同一对象的其他事务提交/放弃后。
- **临时版本**：事务所有写先落在自己的临时版本里（对外不可见），提交时才替换正式版本——放弃时直接扔掉临时版本，天然无副作用。这是乐观方法和时间戳排序共用的基础设施。

### 5.5 锁（悲观方法）【考点】

**基本机制**：事务访问对象前先加锁；锁被别人占着就挂起等待。用锁串行化事务后，冲突操作对自然排成一致次序。

**两阶段加锁（2PL）**【考点】：光有锁还不够——若 T 用完对象 i 就释放 i 的锁、之后又要 j 的锁，而 U 恰好夹在中间，冲突对的次序就可能不一致。因此规定：**事务一旦释放了任何一个锁，就不得再申请新锁**。于是每个事务的生命周期分两段：**增长阶段**（只取锁）→ **收缩阶段**（只放锁）。目的：防更新丢失和不一致检索。

**严格的两阶段加锁**【考点】：更严——**所有锁持有到事务提交（或放弃）之后**才释放（且要等更新对象写入持久存储）。目的：防脏读与过早写（保证可恢复性）。代价是并发度更低（锁要握到事务结束）。

**读锁与写锁**（提升并发度）：read–read 不冲突，所以允许多事务**同时持读锁**；写需要写锁。相容矩阵【考点】（已持有 → 被请求）：

| 已持有 \ 请求 | read | write |
|---|---|---|
| none | OK | OK |
| read | OK | 等待 |
| write | 等待 | 等待 |

**粒度**：若一把大锁锁所有对象，银行里任意时刻只可能有一个柜台在办事——访问需要串行化的**部分对象**应尽量少，即粒度要细。

**死锁**【考点】：一组事务循环等待对方持有的锁（T 持 A 等 B，U 持 B 等 A）。三种对策：
- **预防**：①事务启动时**一次锁住全部**要访问的对象（原子、无死锁；缺点：限制并发 + 未必能预知要访问什么）；②**预定次序加锁**（全系统约定对象加锁顺序；缺点：过早加锁、降并发）。
- **检测**：维护**等待图**（事务为点，"等待"为边），发现环就放弃环中一个事务（牺牲者选择要考虑已运行时间和涉及的环路数）；还要权衡检测频率。
- **锁超时**（最常用）：每把锁有期限，超时变成"可剥夺锁"；有事务等待时即可剥夺（放弃持有者）。缺点：没有死锁也可能误伤——长事务经常被无妄放弃。

### 5.6 乐观并发控制【考点】

**动机**：锁的缺点——维护开销大；只读事务（不可能破坏一致性）也得加锁，锁只在"最坏情况"有用；可能死锁（超时/检测对交互式应用都不理想）；为防连锁放弃锁握到事务结束，并发度低。

**基于事实**：大多数应用里两个客户事务访问同一对象的可能性很低——那就先别检查，**提交时再验证**，冲突了放弃重来。

**三阶段**【考点】：
1. **工作阶段**：事务随便读改，但写落在**临时版本**（放弃无副作用、对他人不可见）；同时维护两个集合——**读集**（读过哪些对象）和**写集**（写过哪些对象）。
2. **验证阶段**：收到 closeTransaction 时检查与其他事务是否冲突；通过则进入更新，失败则放弃（或放弃对方）。
3. **更新阶段**：只读事务立即提交；写事务把临时版本写入持久存储后提交。

**验证的依据**：事务号 Tv（升序分配，按序验证与提交，定义了事务的时间位置）。验证检查 Tv 与**重叠事务 Ti**（Tv 启动时尚未提交的事务）之间的三类冲突：
- 规则 1（Ti read ← Tv write）：Ti 不能读 Tv 写的对象；
- 规则 2（Tv read ← Ti write）：Tv 不能读 Ti 写的对象；
- 规则 3（write–write）：互不能写对方写的对象——由于**同一时刻只允许一个事务处于验证/更新阶段**，Tv 与 Ti 在更新阶段不重叠，规则 3 自动满足；实际只需检查规则 1、2。

**向后验证（backward validation）**【考点】："向过去验证"——与**较早的、已提交**的重叠事务 Ti 比：
- 规则 1 自动满足（Ti 读的时候 Tv 还没写）；只需查**规则 2**；
- 检查内容：**Tv 的读集 ∩ 各 Ti 的写集**；
- 伪代码：`for Ti in (startTn+1 .. finishTn): if readset(Tv) ∩ writeset(Ti) ≠ ∅ → 放弃 Tv`；
- 需要额外保存**已提交事务的写集**（保存到所有重叠事务结束）；
- 语义：并发执行等价于串行次序 **Ti → Tv**（先 Ti 后 Tv）；
- 改进（课件讨论题）：只需比较 **Tv 在 Ti 提交之前已读的那部分读集**——提交后才读的成员不可能读到 Ti 的旧值，判冲突过严。
- 冲突解决：放弃当前验证的事务（简单）。

**向前验证（forward validation）**【考点】："向未来验证"——与**活动事务**（还在工作阶段的 Tid）比：
- 规则 2 自动满足（活动事务在 Tv 完成前不会写）；只需查**规则 1**；
- 检查内容：**Tv 的写集 ∩ 各活动事务的读集**；
- 冲突解决**更灵活**：放弃 Tv；或推迟验证再试；或**放弃所有冲突的活动事务、提交 Tv**；
- 限制：**验证期间不允许启动新事务**（否则新事务可能读到与判定相悖的值）；
- 语义：等价于串行次序 **Tv → Ti**。

**两者比较 + 饥饿**：向前验证用**较小的写集**（写集通常小于读集）比、冲突处理灵活；向后验证要保存已提交事务的写集但允许验证时开新事务。**饥饿**：某事务因冲突被反复放弃永远提交不了 → 用信号量把验证阶段做成互斥区，保证每个事务终能轮到验证。

### 5.7 时间戳排序【考点】

**思想**：不等待、不事后验证——每个事务启动时领一个唯一时间戳，**静态地**把它钉在串行次序的某个位置上；之后每个操作执行前按规则裁决"这个操作符不符合你所处的位置"。

**数据结构**：每个对象有一个**提交版本**（带写时间戳 WTS，比所有临时版本都早）和若干**临时版本**（各事务的未提交写）；读时间戳集合用其最大值 RTS 代表；事务的读操作作用于"写时间戳 ≤ 该事务时间戳的最大版本"。

**写规则**（结合冲突规则 1、2——"写得是否太晚"）：事务 Tc 写对象 D：

```
if (Tc ≥ D 的最大读时间戳 && Tc > D 提交版本的写时间戳)
    在 D 的临时版本上执行写，写时间戳置为 Tc
else
    放弃事务 Tc   // 已经有"更晚"的事务读过或写过 D，你按位置不该再写
```

**读规则**（结合规则 3）：事务 Tc 读对象 D：

```
if (Tc ≥ D 提交版本的写时间戳) {
    设 Dsel = D 的写时间戳 ≤ Tc 的最大版本；
    if (Dsel 已提交) 直接读 Dsel;
    else 等待该事务提交/放弃，然后重新应用读规则;
} else
    放弃事务 Tc;
```

直觉：如果已经有时间戳比你大的事务写过 D，你按位置"在过去"，不该再读到别的结果——干脆放弃重来（你本该拿到更大的时间戳）。**特点：冲突即放弃，无等待、无死锁**；对只读事务友好。

### 5.8 并发控制方法的比较【考点】

| 方法 | 串行次序 | 优势场景 | 冲突时的行为 |
|---|---|---|---|
| 时间戳排序 | **静态**（启动时定） | 读操作占优的事务 | 立即放弃（无等待） |
| 两阶段加锁 | **动态**（运行时竞争锁） | 更新操作占优的事务 | 等待；可能死锁后再放弃 |
| 乐观方法 | 验证时定 | 冲突很少的负载 | 提交时发现冲突，放弃重做 |

时间戳排序与 2PL 均属**悲观**方法（假定冲突会发生）；乐观方法在冲突少的场景性能最高，但放弃时要做大量重复工作。悲观方法实现简单、并发度低。

## 第 6 章 分布式事务

> 本章主线：事务的对象分散在多台服务器上时，"原子性"要求它们对提交/放弃达成**完全一致**的决定——这就是原子提交问题；标准答案是两阶段提交（2PC）。此外还要处理三件事：并发控制怎么跨机器保持一致、死锁怎么跨机器检测、崩溃后怎么恢复。

### 6.1 分布式事务概念【考点】

**定义**：访问**多个服务器**所管理对象的事务（客户事务调用了不同服务器上的操作）。约束：事务结束时，**所有参与服务器必须全部提交或全部放弃**；由其中一个服务器担任**协调者**保证大家得到相同结果。

- **平面事务**：客户给多个服务器发请求，但**完成一个请求才发下一个**——顺序访问各服务器对象；加锁时一次只等一个对象。
- **嵌套事务**：顶层事务可创建子事务，子事务可任意深度再嵌套；**同层子事务可并发**；**父事务可在部分子事务放弃的情况下提交**。

**协调者与参与者**【考点】：协调者负责事务的开始、提交、放弃——即收到 openTransaction 的那台服务器；客户在任意服务器上发 openTransaction，得到 TID（= 创建服务器标识(IP) + 该服务器内唯一数字）。协调者接口里的 **join** 方法把新参与者加入事务。**协调者知道所有参与者，每个参与者也知道协调者**（这句话决定了后面消息流向）。例：T 跨 BranchX(A)、BranchY(B)、BranchZ(C,D) 转账，每台服务器一个参与者依次 join。

### 6.2 原子提交协议的概念【考点】

**原子提交协议**：让所有服务器互相通信、共同决定提交或放弃的协议。原子提交问题：要么全提交，要么全放弃；**任何节点崩溃 → 全部放弃**。

**与共识的异同**【考点】（判断题爱考"它们一样吗"）：像——都是就某个决定达成一致；**本质不同**：
- 共识：一个/多个节点提议，可以从被提议的值里**挑一个**；能容忍少数节点崩溃（只要法定人数活着就继续）。
- 原子提交：所有节点必须投票 commit 或 abort；**全票 commit 才提交，任何一人投 abort（或崩溃）就放弃**——一个参与者都不能丢。

### 6.3 单阶段原子提交协议及缺陷【考点】

做法：协调者直接向所有参与者发 Commit 或 Abort，反复发送直到全部确认。

**缺陷**：**不允许参与者单方面决定放弃**——但现实中存在协调者不知道的放弃理由：并发控制问题阻止了本地提交（为解除死锁要放弃、乐观验证失败）、参与者崩溃需要放弃。一方已经放弃而协调者还在发 Commit，原子性即被破坏。**结论：单阶段协议不充分。**

### 6.4 两阶段提交协议（2PC）【考点】

**设计动机**：让**任意参与者能自行放弃**自己那部分事务——所以要先"投票"：每个人表态，有人说不就不干。

**基本思想**：一个协调者 + 多个参与者；第一阶段问所有人"能否提交"，第二阶段按投票结果统一通知提交或放弃。

**五个基本操作**【考点】（要能默写名字和用途）：
- `canCommit?(trans) -> Yes/No`：协调者询问；参与者**投 Yes 前必须先把对象存入持久存储**（"准备提交"），投 No 则立即放弃；
- `doCommit(trans)`：通知参与者提交其那部分；
- `doAbort(trans)`：通知放弃；
- `haveCommitted(trans, participant)`：参与者向协调者确认已提交（供协调者清理过时信息）；
- `getDecision(trans) -> Yes/No`：参与者投了 Yes 却迟迟没收到决议时，**向协调者查询表决结果**——从崩溃或消息延迟中恢复的关键。

**过程描述**【考点】：
- **阶段 1（投票）**：协调者向所有参与者发 canCommit?；参与者投 Yes（先持久化，进入"准备提交"状态）或 No（立即放弃）。
- **阶段 2（决定）**：协调者收集全部投票（含自己）：
  - (i) 无故障且**全部 Yes** → 决定**提交**，向所有参与者发 doCommit；
  - (ii) 否则 → 决定**放弃**，向所有投 Yes 的参与者发 doAbort（投 No 的已经自己放弃了，不用通知）。
  - 投 Yes 的参与者收到任一决议后执行；若是提交，还要回 haveCommitted。

状态视角：协调者——等待投票 → 提交/放弃 → 完成；参与者——准备提交 → **（不确定 uncertain）** → 已提交。**"不确定"状态是理解 2PC 一切问题的钥匙**：投了 Yes 之后、收到决议之前，参与者既不能提交也不能放弃——它不知道最终结局，问谁？只能问协调者。

**各种消息丢失的处理**【考点】（分析题常考）：
- **canCommit? 丢失**：参与者等不到询问，超时后**单方面放弃**（协调者那边最终也会放弃，一致）；
- **Yes/No 投票丢失**：协调者凑不齐全票，超时后**放弃**（悲观策略），并向投了 Yes 的人补发 doAbort；
- **doCommit 丢失**：参与者等不到决议，超时后发 **getDecision**（重试直到得到答复）；注意此时**绝不能单方面放弃**——协调者可能已决定提交；
- **haveCommitted 丢失**：事务仍正确提交，只是协调者多留了一阵过时信息；
- **参与者投 Yes 后崩溃**：因为投票前已把对象写入持久存储，重启后照样能提交——事务仍正确。

**性能**【考点】：N 个参与者、无故障时共 **3N 条消息**（N 个 canCommit + N 个投票 + N 个 doCommit；若算 haveCommitted 则为 4N）。最坏情况（崩溃与延迟任意）：参与者可能长时间滞留在"不确定"状态。

**缺陷**【考点】（必背三条，DS.pdf 作业原题）：
1. **同步阻塞**：从投 Yes 到收到决议之间，所有参与者阻塞、什么都做不了；若协调者在发起提议后崩溃，投 Yes 者要阻塞到协调者恢复；
2. **单点故障**：协调者既是性能瓶颈又是单点失效；
3. **数据不一致**：协调者发出 doCommit 后若局部网络异常或它自己没发完就崩溃——只有部分参与者收到 doCommit，收到者提交、没收到者（在"不确定"里）不敢提交 → 副本间不一致。

（改进方向：**3PC** 把第二阶段再拆出一个**预提交**阶段，参与者在协调者故障时可以依据自身和其他参与者的状态推断事务结局，从而降低阻塞；代价是消息更多、协议更复杂。）

### 6.5 分布式事务的并发控制（锁方法）【考点】

- **本地并发控制**：每台服务器对自己的对象施加并发控制（锁/时间戳/乐观），多台服务器的本地控制共同构成分布式并发控制。
- **分布式串行等价的要求**：若事务 T 在某一服务器上先于 U 访问了冲突对象，那么**在所有服务器上** T 都必须先于 U——否则各机器"各串各的"，整体不串行。
- **加锁**：对象锁是**本地特有**的，是否加锁由本地锁管理器决定；基于本地加锁可以实现分布式串行等价（只要各服务器对同一对事务的加锁次序一致，例如都先 A 后 B）。问题：持锁等待跨越多台服务器——T 在 X 持 A 等 Y 上的 B，U 在 Y 持 B 等 X 上的 A——**分布式锁极易死锁**。
- **时间戳并发控制**：可行，但协调者必须保证时间戳**唯一且全序**。做法：时间戳 = ⟨本地时间戳, 服务器 id⟩，先比本地、再比 id。**即使各服务器时钟不同步也能保证全序**——比 id 的兜底保证了任何两台机器产出的大小关系一致。
- **乐观并发控制**：2PC 性能低，所以分布式乐观验证要**允许多个事务并行验证**；风险是不同服务器可能把同一组事务串成不同次序（X 上 T 先 U 后，Y 上 U 先 T 后）→ 破坏串行等价；对策之一是使用**全局唯一的事务号**统一排序。

### 6.6 分布式死锁产生原因及检测方法【考点】

**成因**：分布式事务要同时持有跨多台服务器的多把锁，锁获取有先后，循环等待更容易形成；超时法在分布式下难以设置合理的超时值、代价大。

**例子（要会画等待图）**：U 持 A(X) 等 B(Y)；V 持 B(Y) 等 C(Z)；W 持 C(Z) 等 A(X) → 环 U→V→W→U 跨越 X/Y/Z 三台服务器。各服务器的**局部等待图**分别只有一条边：X: W→U；Y: U→V；Z: V→W——**任何一台单独看都没有环**；检测必须在拼出来的**全局等待图**里找环。

**方法一：集中式死锁检测**：某台服务器担任全局检测器，收集各局部等待图拼出全局图，发现环就制定方案并通知相关服务器放弃相应事务。不足：依赖单一服务器（可靠性差、无容错、无伸缩性）、收集局部图的通信代价高。

**方法二：边追逐（分布式检测）**【考点】：不构建全局图，让"探测消息"沿等待边游走：
- **开始**：服务器发现事务 T 开始等待 U，而 U 正在等另一台服务器上的对象 → 发出探测消息 probe ⟨T→U⟩（记录发起检测的事务）；
- **检测/转发**：收到 probe 的服务器判断是否构成环（probe 回到发起者即有环），不成环则沿 U 的等待边继续转发；
- **解除**：检出环后放弃环中一个事务。

**性能**【考点】：探测消息每转发一次要 2 条消息（对象服务器 → 事务协调者 → 协调者所等对象的服务器）；涉及 N 个事务的死锁，probe 要经 N−1 个协调者、N−1 个对象服务器转发，共 **2(N−1)** 条消息。

**解除的坑**：环上每个事务都可能各自发起检测 → 多台服务器独立决定、可能放弃**不同**的事务 → 不必要的多杀。对策：按**事务优先级**决定只放弃优先级最高（或最低）的那个。

### 6.7 两阶段提交协议的恢复【考点】

**事务恢复**的目标 = **持久性**（对象保存于持久存储并可用）+ **故障原子性**（即使服务器中途崩溃，事务的更新效果也要么全有要么全无）。恢复的实质：按持久存储中**最后提交的对象版本**恢复服务器中的对象值。

**意图列表**：每个活动事务一份，记录它修改的对象 ⟨ObjectID, 位置 Pi⟩。用途：提交时据此把临时版本替换成正式版本；放弃时据此删除全部临时版本。

**日志（恢复文件）**：服务器执行过的全部事务历史，由三类记录构成——对象值、事务状态（prepared/committed）、意图列表；每条事务状态记录带指向前一条的指针形成链；定期打**检查点**加速恢复。

**2PC 在日志里新增**：两个状态——**done（完成）**与 **uncertain（不确定）**；两种记录——协调者记"事务标识 + 参与者列表"，参与者记"事务标识 + 协调者"（恢复时靠它知道该找谁要决议）。

**恢复动作表**【考点】（必背，按"角色 × 崩溃时状态"组织）：

| 角色 | 崩溃时状态 | 恢复后的动作 |
|---|---|---|
| 协调者 | 准备好（尚未做决定） | 未做过任何决定 → 向参与者列表全员发 **doAbort**，并记录"已放弃"（若无参与者列表，参与者会因超时自行放弃） |
| 协调者 | 已提交 | 已决定提交 → 向所有参与者重发 **doCommit**，继续执行协议第 2.2 步 |
| 协调者 | 完成 | 无需任何操作 |
| 参与者 | 已提交 | 向协调者发 **haveCommitted**，让协调者能在下个检查点丢弃该事务信息 |
| 参与者 | 不确定 | 决议未拿到就崩了 → 发 **getDecision** 向协调者查询，得到答复后再提交或放弃 |
| 参与者 | 准备好（尚未投票） | 可以**单方面放弃** |

## 第 7 章 复制

> 本章主线：把数据复制到多台机器是为了性能、可用性、容错——但副本会带来新问题：**更新之后大家还一致吗？** 于是有一致性谱系（从强到弱）、两种系统模型（主动/被动复制）、事务复制方案（读一/写所有），以及用弱一致性换高可用的极致设计——Gossip。

### 7.1 复制的概念、动机、基本要求【考点】

**概念**：在多个节点保存相同数据的副本；持有副本的节点叫**副本管理器（Replica Manager, RM）**。数据库、文件系统、缓存系统都用。

**动机**【考点】三组：
- **增强性能**：负载均衡（如 DNS、Web，系统可扩展）、资源缓存（就近服务减少延迟，如在线视频）；
- **提高可用性**：n 个独立副本全挂的概率 1 − pⁿ 随 n 指数下降；还能提前复制以对付网络分区与断链操作；
- **增强容错**：容忍一定数量、一定类型的故障（崩溃、拜占庭）——此时关心正确性：客户拿到的数据是否最新、操作结果是否正确。

**基本要求**【考点】：**复制透明性**（对客户屏蔽多个物理拷贝的存在，客户只看到一个逻辑对象）+ **一致性**（对复制对象集合的操作满足应用要求的一致强度——注意强度是分级的，见 7.3）。

### 7.2 系统模型

- 基本模型：客户 → **前端 FE** → 一组副本管理器 RM。FE 替客户与多个 RM 通信（选可用的、响应快的）；**RM = 副本 + 操作副本的组件**，本质是一个**状态机**：当前状态 + 一串操作 ⇒ 唯一确定的新状态（所以只要大家以相同次序执行相同操作，状态就一致——这是主动复制的理论根据）。
- 副本对象操作的五步【考点】：**请求**（FE 发给一个或多个 RM）→ **协调**（保证一致地执行：是否执行要一致、相对次序要确定）→ **执行**（RM 执行请求，效果可撤销）→ **协定**（就提交/放弃达成一致）→ **响应**（RM 回 FE，FE 回客户）。
- 三种次序保证【考点】：**FIFO**（同一 FE 的请求 r 先于 r' 发出，则处理 r' 的 RM 必先处理了 r）；**因果序**（r → r' 则先 r 后 r'）；**全序**（所有正确 RM 以相同次序处理）。

### 7.3 四种一致性【考点】

一致性从强到弱排成一条谱线，**区分它们的钥匙是"允许重排到什么程度"**：

- **可线性化（Linearizability）**：存在一个**与实时序一致**的全体操作交错序列，且该序列符合单副本的规约。效果：整个系统仿佛**只有一个副本**——任何客户的读都返回"最近一次写"的值，"最近"由**物理时间**决定。这就是 CAP 里的 C。实现技术：链式复制、主备份（被动）复制。
- **顺序一致性（Sequential consistency）**：存在符合单副本规约的交错序列，且**保持每个客户自己程序里的次序**；但**不同客户之间的次序可以重排**——不由时间决定，系统自由选。可线性化与顺序一致性的区别【考点】：都营造"单副本错觉"；线性化关心**时间**，顺序一致性只关心**程序次序**。
  - 课件例子（判断练习）：客户1 做 setBalanceB(x,1)、setBalanceA(y,2)；客户2 读到 y=2、x=0——同一客户内顺序没错，但跨客户看像"先 y 后 x"，**不满足顺序一致性**；若客户2 读到 y=0、x=0——满足顺序一致但**不满足线性化**（setBalanceB(x,1) 在时间上先于读，读却没看到 1）；若读到 y=0、x=1——两者都满足。
- **因果一致性**【考点】：所有进程以**相同次序**看到**因果相关**的写；**并发写**允许不同进程看到不同次序。因果关系怎么定义：一个客户读了另一个客户写的数据、随后自己又写——这两个写就是因果相关的。判断方法：先把写分成"因果链"与"并发"两组，因果链上的次序不能乱、并发随便。它弱于顺序一致（连"单副本错觉"都不要了）。
- **最终一致性**【考点】：副本管理器只按本地状态处理操作（网络分区时各分区各自提交冲突事务）；只要**不再有新更新**，最终所有副本会收敛到相同状态——但**不保证多长时间**收敛。背景：网络分区把 RM 组切成互不相通的子组——阻塞服务保一致（对外不可用）vs 继续服务保可用（副本分歧），这就是 **CAP**：分区存在时一致性与可用性只能二选一；**BASE**（基本可用 + 软状态 + 最终一致）是工程上的和解方案。

### 7.4 复制的系统模型：主动复制、被动复制【考点】

**被动复制（主备份，primary-based）**：
- 结构：**一个主 RM + 多个备份 RM**；FE 只把请求发给**主**；主崩溃时某个备份提升为主。
- 五步的落法：请求 → FE 只发主；**协调 → 主按接收次序为请求排序**；执行 → 主依次执行并暂存应答；协定 → 更新操作则把**新状态 + 应答 + 唯一标识**发给每个备份、等确认；响应 → 主应答 FE。
- 一致性结论【考点】：**具备可线性化**——一切次序都由主按实时接收次序拍板，时间序天然保留。

**主动复制（active replication）**：
- 结构：RM **地位对等**；FE 用**全序、可靠组播**把请求发给**所有** RM。
- 五步的落法：请求 → 组播；协调 → 组通信系统把请求以**相同（全序）次序**传给每个 RM；执行 → 每个 RM 以相同方式执行（状态机同构）；协定 → **不需要**（全序可靠组播的语义已保证）；响应 → 每个 RM 都应答，FE 视故障模型收集若干个。
- 一致性结论【考点】：**只具备顺序一致性、不具备线性化**——全序是系统自己排的，未必与客户发请求的**实时**次序相同。

记忆：**被动=主定序=线性化；主动=组播定序=顺序一致**。

### 7.5 单拷贝串行化、"读一/写所有"方案及本地验证【考点】

**单拷贝串行化（one-copy serializability）**：客户在**复制对象**上执行事务的效果，应当与它们在"每个对象只有 **1 个副本**"的对象集合上逐一执行相同。直觉：= **串行等价**（第 5 章）+ **复制透明**，把非复制系统的正确性标准平移到复制系统。

**读一/写所有（read-one/write-all）**方案：
- **读请求由单个 RM 执行**（读读不冲突，随便挑一个，还能分散负载）；
- **写请求必须由所有 RM 执行**（对对象加锁，保证每个副本都更新）。
- 只要事务执行期间可用副本集不变，本地并发控制（锁）即可获得单拷贝串行化——例：T 读 A（锁 A[X]）、U 读 B（锁 B[N]），T 写 B 时要在**所有**副本上锁 B、U 写 A 时在所有副本上锁 A → 冲突对的次序全局一致（可能死锁，但死锁可检测，**串行等价有保证**）。

**可用副本复制（available copies）**：现实里"写所有"做不到——副本会崩溃、会失联。放松为：读由**任何可用** RM 执行，写由**所有可用** RM 执行。**前提：事务执行期间可用副本集不变**。

**为什么前提会被破坏（要会推演课件的反例）**：T 读 A[X]、U 读 B[N] 之后，X 与 N 先后崩溃 → T 的写 B 在 M、P 上执行，U 的写 A 在 Y 上执行 → 对象 A 上先 T 后 U、对象 B 上先 U 后 T → 冲突对方向不一致 → **不再是单拷贝串行化**（崩溃让锁失效了，另一个分区上的副本毫不知情）。

**本地验证（local validation）**【考点】：提交前检查"执行期间我访问的副本集有没有发生变化（故障或恢复）"，变了就放弃事务。两个检查方向：
- **可用 → 故障**：利用 2PC 的提交阶段确认所有无故障的 RM 在提交时仍然活着（故障了提交即失败）；
- **故障 → 恢复**：定期联系故障节点，确认它没有在我事务执行期间悄悄复活。
- 结论：基于本地验证，可用副本复制可以保证单拷贝串行化。

### 7.6 闲聊（Gossip）系统【考点】

**定位**：容错服务（所有正确 RM 及时收到更新、响应前达成一致）代价高；**高可用服务**反其道行之——**用更弱的一致性换可用性**。Gossip（又称反熵 Anti-Entropy）：节点随机地互相交换更新，像传播八卦，最终全体一致。目标：客户落到任一分区，只要该分区有一个活着的 RM，就能获得服务。

**两个保证**【考点】：
1. **副本管理器提供的数据能反映客户迄今已观测到的更新**（随时间推移，每个用户总能获得一致的服务）——读不会"倒退"；
2. **副本之间松弛一致**：所有 RM **最终**收到所有更新——但两个客户可能看到不同副本、客户可能读到过时数据。

**体系结构与关键数据结构**【考点】（这是简答重点，要说出每个结构"为什么存在"）：
- **前端 FE 的版本时间戳**：一个向量时间戳（每个 RM 一个分量），记录**客户已经观察到哪些更新**；随每个请求携带，收到响应后 merge 进来。存在理由：保证 1——服务方必须知道客户见过什么，才不会给出"倒退"的数据。
- **副本管理器 RM 的五件套**：
  - **值 val**：应用状态（由初始值 + 已施加的全部更新决定）；
  - **值时间戳 val.ts**：已**稳定**的更新的向量时间戳（"稳定"= 已实际生效于值）；
  - **副本时间戳 replica.ts**：本 RM **收到过**的所有更新的时间戳（含尚未生效、压在日志里的）；
  - **更新（副本）日志 log**：记录 ⟨i, ts, u.op, u.prev, u.id⟩（i=创建者编号、ts=更新时间戳、u.op=操作、u.prev=前端时间戳、u.id=唯一标识）。存在理由：不满足次序保证的更新不能立刻执行，必须先攒着；
  - **已执行操作表 executed**：已执行更新的唯一标识集合——**防重复执行**（gossip 消息会重复到达）；
  - **时间戳表 tableTS**：来自 gossip 消息，记录"我知道别人各自收到了谁的前多少个更新"，如 (2,4,5) = 从 RM0 的前端收到 2 个、RM1 的前 4 个、RM2 的前 5 个。存在理由：判断一条日志**何时可以安全删除**（所有人都收到了）。

**查询操作**【考点】：RMi 收到查询 q：
- 若 **q.pre ≤ rmi.val.ts**（前端已知的时间不超过本 RM 已稳定的值的时间戳）→ 满足保证 1，返回 (val, val.ts)；
- 否则 → 消息进**保留队列阻塞等待**（宁可让客户等，也不给过时数据）。例：q.pre=(2,1,0) > rm2.val.ts=(1,0,0)，rm2 还没收到 RM0 的第 2 个更新 → 阻塞。
- 前端收到响应后 merge 时间戳：frontEndTS := merge(frontEndTS, rm.val.ts)。

**更新操作**【考点】：FE 发 (u.op, u.prev, u.id)；RMi 收到：
1. 按 u.id 查重，已处理过则**丢弃**；
2. 否则：**rmi.replica.ts[i] += 1**；构造更新时间戳 ts = u.prev（把前端已知的时间全继承），再**把第 i 个分量替换为 replica.ts[i]**；日志追加 ⟨i, ts, u.op, u.prev, u.id⟩；把 ts 返回 FE（FE merge）。
3. **按因果次序执行**：对日志中未执行的记录 r，检查**稳定性条件**：**r.u.prev ≤ rmi.val.ts**（该更新所依赖的前端状态，本 RM 都已稳定）→ 满足则执行：val := apply(val, r.u.op)；val.ts := merge(val.ts, r.ts)；executed ∪= {r.u.id}；不满足则**推迟**。推迟的价值（讲义实例）：rm2 晚收到 x=3（它依赖 x=2）时，即使 x=3 的记录先到，也会先压着，等 x=2 稳定后按因果次序执行——这就是**因果一致性**的落实处。

**gossip 消息**【考点】：格式 = **日志 m.log + 副本时间戳 m.ts**。RM b 收到 a 的 gossip：
- 若 **rma.replica.ts ≤ rmb.replica.ts**（b 已经全都知道）→ **丢弃**；
- 否则：合并副本时间戳 replica.ts = merge(两者)；把 a 的日志合并进本地日志；然后执行所有"未执行且已满足稳定条件"的更新。

**日志删除**【考点】：日志不能无限涨。创建者 c 的记录 r 可删除 ⟺ **所有** RM i 满足 **tableTS[i][c] ≥ r.ts[c]**——所有人都收到过这条更新了，它已完成历史使命。讲义给出了正反两例：全部满足时可删；rm2 还差一个更新时，rm1 里的对应记录就**不可删**。

**传播策略**：协议不规定发送频率（分钟/小时/天由应用定）与合作者选择——随机（加权概率，如近的优先）、确定（状态函数，如选更新最旧的）、拓扑（固定成网格/环/树）。

**强制/即时更新**：需要全序 + 因果序——在时间戳后追加唯一序号并按序处理，通常指派一个**主 RM** 定序。

**局限**【考点】：不适合接近实时的更新复制（如多人实时编辑）；可扩展性——RM 数量增长，gossip 消息数量与时间戳长度（向量维度）同步增长。

## 第 8 章 分布式文件系统

> 本章主线：让远程文件用起来像本地文件（透明性），难点在"客户缓存了数据，服务器改了怎么办"——NFS 用"无状态 + 客户端时间戳验证"，AFS 用"整体文件 + 回调承诺"，两条路线对比着记。

### 8.1 分布式文件系统的需求【考点】

先回忆本地文件系统的分层模块（目录模块：文件名↔文件 ID；文件模块：ID↔物理文件；存取/块/设备模块）——DFS 的目标就是**模拟本地文件系统的行为**（文件没复制、无严格性能保证，只是文件在远程、多客户共享）。

需求【考点】：
1. **透明性**：访问透明（同一组文件操作访问本地/远程文件）、位置透明（全系统单一命名空间，所有用户看到同样的名字）、移动透明（文件被移动，客户的配置不用改）、性能透明（负载变化时性能仍可接受）、伸缩透明（加服务器即可扩容）；
2. **并发的文件更新**：并发控制，一个客户的修改不影响其他客户；
3. **文件复制**：分摊负载、容错；
4. **硬件与 OS 异构性**：接口定义明确，不同平台实现同一服务；
5. **容错**【考点】：瞬时通信故障要能对付——要么最多一次调用语义，要么**幂等操作**支持最少一次语义（重复执行效果同一次）；**无状态服务器**：崩溃后重启无需任何恢复；
6. **一致性**：**单个拷贝更新语义**——多进程并发访问时仿佛只有一个文件拷贝；
7. **安全性**：客户请求要认证，访问控制基于正确身份；
8. **效率**：不慢于本地文件系统的可接受水平。

调用语义对照（笔记）：at most once（可丢不可重，最高效）；at least once（可重不可丢，需重传+幂等）；exactly once（最难实现，需协调）。

### 8.2 文件服务体系结构：三个组件【考点】

抽象模型把文件服务拆成三块（NFS/AFS 都能映射回这个模型）：

- **平面文件服务**：只管**文件内容**，按 **UFID**（唯一文件标识）寻址。操作：create、delete、read(FileId, i, n)→data、write(FileId, i, data)——read/write 都带**位置参数 i**。
  - 与 UNIX 的对比及容错意义【考点】：**没有 open/close**（拿 UFID 直接访问，无需读写指针）→ 除了 create（每次产生新文件）外**所有操作都幂等**（read/write 带绝对位置，重复执行结果不变）→ 可以放心重试 → 支持 at least once 语义；**无状态服务器**：服务器不保存任何会话信息，崩溃重启后客户什么都不用恢复。UNIX 的 open 会生成读写指针，既非幂等也与无状态矛盾。
- **目录服务**：管**名字 → UFID 的映射**和层次目录（目录是特殊文件）；含元数据（创建/修改/访问时间等）。核心操作 Lookup(Dir, Name)→FileId，另有 AddName/UnName/GetNames。
- **客户模块**：运行在客户机上，对应用透明地访问远程服务；**缓存最近使用的文件块**提升性能。

**访问控制**：DFS 接口公开有安全隐患；无状态服务器不能保存 UID（否则就有状态了）→ 两个办法：基于权能（用户持访问能力列表）或**每个请求携带 UID、每次检查**；NFS 和 AFS 都用 **Kerberos** 解决伪造身份问题。

### 8.3 NFS 体系结构、服务器操作、路径解析、缓存机制【考点】

**体系结构**：客户机与服务器都插在 UNIX 内核的 **VFS（虚拟文件系统）**层——一个转换层，支持 EXT2/NTFS/NFS 等多文件系统共存、区分本地/远程、把请求转发给适当的文件系统。**V 节点**是 VFS 的统一句柄：本地文件 → 引用 i 节点；远程文件 → 引用**文件句柄**。

**文件句柄（三段式）**【考点】= **文件系统标识符**（服务器可能服务多个文件系统）+ **i 节点数**（文件系统内唯一，标识并定位文件）+ **i 节点产生数**（i 节点删除后可重用，每次重用 +1；防止"句柄还开着、文件被删重用"的张冠李戴——产生数变了就抛异常）。句柄在客户与服务器间传递，**对客户不透明**。

**NFS 服务器是无状态的**【考点】（与 UNIX 传统不同）：每个新请求都要重新验证——UID 绑定在每个请求上，服务器逐请求核对访问权限；配合 Kerberos 在安装时认证。

**服务器操作**（RFC 1813，记要点即可）：lookup(dirfh, name)→fh、create、remove、getattr/setattr、**read(fh, offset, count)→attr, data**、**write(fh, offset, count, data)**、rename、link/symlink/readlink、mkdir/rmdir、readdir(dirfh, cookie, count)（cookie 是不透明的续读指针）、statfs。

**安装（mount）服务**：每台服务器用 **/etc/exports** 声明本地哪些子树可被远程安装；客户用 mount 把远程目录挂进本地命名空间（如服务器1 的 /export/people 挂到客户 /usr/students）——远程文件从此像本地文件一样按路径访问。

**路径解析**【考点】：**NFS 服务器不做路径名转换**——翻译由**客户**以交互方式完成：客户对路径**逐段**发 lookup 请求，把每一部分换成文件句柄（例：/programs/pong.c → 根 i 节点找到 programs 的 inode 7 → lookup 得 pong.c 的 inode 9 → 得到数据块）。为什么这样设计：服务器保持无状态（不能替客户维护"解析到一半"的上下文），且中间结果（句柄）可缓存。

**服务器缓存**【考点】：
- 读缓存：与本地文件系统相同（预先读、把常用页驻内存、延迟写 + 周期性同步写防丢失）；
- 写缓存两种模式【考点】：**写透 write-through**——应答客户**之前**先写盘（持久性好，但可能成为性能瓶颈）；**内存缓存**——写先驻内存，收到相关文件的 **commit**（关闭为写而打开的文件时）再落盘（性能好）。

**客户缓存及其一致性**【考点】（计算/简答热点）：客户缓存 read/write/getattr/lookup/readdir 的结果，减少对服务器的请求。一致性靠**基于时间戳的验证**——每个缓存块记两个时间戳：
- **Tc**：该缓存条目**上次被验证**的时刻；**Tm**：服务器上该文件块**上次被修改**的时刻；
- **有效性条件：(T − Tc < t) 或 (Tmclient = Tmserver)**——没过期就直接用（省一次 RPC）；过期了就用 getattr 向服务器要最新 Tmserver 比对，一致才继续用；
- **t** 是更新间隔：文件 3~30 秒、目录 30~60 秒（目录更新风险低所以更长）——一致性与效率的折衷参数；
- 注意：该机制**不能**保证与真正 UNIX 一致的一致性（有 t 秒的窗口）；
- 减少 getattr 调用的三个技巧：收到新 Tmserver 后套用到相关文件的派生缓存项；每次文件操作的结果都附带当前属性；用自适应算法调 t。

### 8.4 AFS 应用场景、设计理念、缓存机制、一致性【考点】

**应用场景与动机**：CMU 校园共享系统（1986），目标是**可扩展性**——5000~10000 个节点、海量用户、海量文件、热点文件（NFS 的客户缓存轮询模式撑不住这个规模）。

**设计理念**【考点】两条：
- **整体文件服务**：服务器把**整个文件**（和目录）一次性传给客户（不是按块）；
- **整体文件缓存**：传来的文件存进客户**本地磁盘缓存**（专用分区，容量大，满时 LRU 淘汰）。
- 设计依据的负载假设：文件较小（多数 <10KB）、读是写的 6 倍、顺序访问为主、文件通常被特定用户使用/修改、最近用过的会再用、不支持数据库文件。**读多写少 + 文件归属集中 ⇒ 缓存命中率会很高 ⇒ 整体文件方案才划算**。

**两个进程**【考点】：**Venus**（运行在客户机上的用户进程，= 抽象模型的客户模块，管缓存）+ **Vice**（服务器软件，每台服务器上的用户级 UNIX 进程）。

**文件标识 fid**：卷号 + 文件句柄 + 唯一标识（类比 NFS 句柄/UFID）；Venus 逐步查找把路径翻译成 fid。修改版 UNIX 内核把指向共享名字空间的 open/close 等系统调用**拦截**交给 Venus 处理。

**典型使用场景（open/close 流程）**【考点】：
1. 客户 open 远程文件：缓存里没有（或回调已失效）→ Venus 找到文件所在服务器，请求**传输整个文件的副本 + 回调承诺**；否则直接用缓存副本；
2. 读写都在**本地副本**上正常进行（不再联网）；
3. close：若文件被更新，Venus 把副本**刷新回服务器**；本地磁盘拷贝保留，供本机后续使用。

**缓存一致性：回调（callback）机制**【考点】：
- **回调承诺**：管理该文件的 Vice 服务器发给 Venus 的一个标识，语义是"**别的客户改这个文件时我会通知你**"；只有**有效/取消**两种状态。
- open 时若回调有效 → **完全不访问服务器**直接用缓存（这就是 AFS 可扩展性的来源：读多写少 ⇒ 绝大多数 open 走本地缓存，客户-服务器交互远少于 NFS 的轮询验证）；
- Vice 执行更新时，通知所有持有该文件回调的 Venus 把回调置为**取消**；
- 客户重启、或长时间收不到任何回调 → 认为缓存失效（兜底）。

**更新语义**：**AFS-1**（强）：成功 open 后 latest(F,S)——客户拿到的 F 与服务器上的相同；成功 close 后 updated(F,S)——客户的修改已传播到服务器；失败则 failure(S)。**AFS-2**（较弱，处理回调丢失）：成功 open 后，latest(F,S) **或** lostCallback(S,Ts) ∧ inCache(F) ∧ latest(F,S,T)——即回调丢失且缓存里本来有该文件时，允许用不超过 T 秒（通常 10 分钟）的旧拷贝。

**其他要点**：只读卷可复制到多台服务器；以 64KB 块批量传输；AFSv3 支持部分文件缓存（只读文件片段时不必拖整文件）；位置数据库（卷名→服务器）每服务器一份；广域网支持多管理单元（cell），各自自治又合成统一名字空间。

**NFS vs AFS 对比**【考点】：NFS——无状态、高效、客户缓存靠时间戳轮询验证、**可扩展性不高**；AFS——整体文件+回调、服务器负载小、**可扩展性好**。

## 第 9 章 谷歌文件系统 GFS

> 本章主线：GFS 的每一条设计都从四条"离经叛道"的假设推出来——组件必坏、文件巨大、追加为主、放松一致性。理解了假设，架构（单 Master + 大 chunk + 多副本）、三种操作流程、一致性模型就全是自然结论。

### 9.1 设计动机、设计思想【考点】

**四条动机**【考点】：
1. **组件失效是常态而非意外**：几百上千台廉价设备 + 海量客户机，任何时刻都有东西坏着 → 系统必须持续自我监控、迅速侦测、冗余、恢复。**这推翻了"先保证不坏再谈性能"的传统设计次序。**
2. **文件非常巨大**：数 GB 的文件很常见；管理数亿个 KB 级小文件不明智 → I/O 与块尺寸都要重新设计（于是有了 64MB 大 chunk）。
3. **文件修改以追加为主**：随机写几乎不存在；写完只顺序读 → 客户端缓存数据块没有意义，**追加操作的性能和原子性成为主要考量**。
4. **API 与文件系统协同设计**：**放松一致性模型的要求**（不追求传统文件系统的强一致）；提供**原子的记录追加**，多客户端并发追加同一文件无需额外同步。

**设计假设与参数**：大量廉价组件（失效常态）、需持续监控自愈；存储大量大文件（百万级文件、通常 100MB+、数 GB 常见；支持小文件但不为它优化）；大规模流式读 + 小规模随机读；大规模顺序追加写；必须高效且**语义明确地**支持多客户端并行追加；**吞吐量比低延迟重要**。

**体系结构总览**【考点】：
- 文件切成固定大小的 **chunk**（数据块），每个 chunk 有全局唯一的 64 位句柄；
- **每个 chunk 至少 3 个副本**，放在不同 chunk 服务器（跨机架），以本地文件形式存于 Linux 文件系统；
- **单一 Master** 维护全部元数据：**文件命名空间、文件→chunk 映射、chunk 位置信息、访问控制信息、chunk 版本号**——只存元数据，不碰文件数据；
- Master 与 chunk 服务器间**心跳**：定期查询状态（宕机？硬盘坏？副本错？持有哪些块）并下发命令（建块/删块）；
- **操作日志**：元数据修改的历史，复制到远端，可从检查点恢复；同时充当**逻辑时间基线**，定义并发操作的执行顺序（文件/chunk/版本号由创建时的逻辑时间唯一永久标识）；
- **缓存策略**：客户和 chunk 服务器都**不缓存文件数据**（流式读或工作集太大，缓存无用；chunk 本来就是本地文件，Linux 页缓存自然管）——客户只缓存**元数据**（chunk 位置）。

### 9.2 Master 不存在性能瓶颈的原因【考点】（五点，必背）

单 Master 是最大胆的设计，靠五条不让它成为瓶颈：
1. **只存元数据、不存文件数据** → 磁盘容量不成为瓶颈；
2. 元数据**同时放磁盘和内存** → 磁盘 I/O 不成为瓶颈；
3. 元数据**内存完全装得下**（每 64MB chunk 仅 64B 元数据）→ 内存不成为瓶颈；
4. **所有数据流、缓存都不经过 Master**——客户拿到位置后直接与 chunkserver 传输 → 带宽不成为瓶颈；
5. 元数据**缓存在客户端**，只有失效时才问 Master → CPU 不成为瓶颈。

副产品：Master 操作快，可以定期后台扫描整个状态——垃圾收集、为均衡负载/磁盘做 chunk 迁移、副本不足时重复制。

### 9.3 读操作流程【考点】

1. 应用发起读：给出（文件名, 字节范围）；
2. GFS client 换算：**chunk 索引 = 偏移量 ÷ 64MB**（例：134,250,297 B = 67,108,864 × 2 + 32,569 → 第 2 块，块内偏移 32,569），把（文件名, chunk 索引）发给 Master；
3. Master 返回 **chunk 句柄 + 各副本位置**；
4. client 选其中一个位置，直接向该 **chunkserver** 发（句柄, 字节范围）；
5. chunkserver 回数据 → client 转交给应用。

要点：client 会缓存（文件名, chunk 索引）→ 句柄/位置的映射，同一块反复读不再问 Master（呼应瓶颈第 5 条）；数据全程**不经过 Master**（呼应第 4 条）。

### 9.4 写操作流程【考点】（控制流与数据流分离）

写要落到**所有副本**，且并发修改必须保证相同次序——次序由 chunk 的**主副本（Primary）**统一裁决：

1. client 问 Master：拿到 chunk 句柄、副本位置，以及**谁是 Primary**；
2. client 把写数据**推**给所有副本（沿网络拓扑流水线式传递），存进各副本的**内存缓存**——这一步只是搬数据，**尚未写盘**；
3. 各副本确认收到后，client 向 **Primary** 发**写命令**（控制流）；
4. Primary 给这个写**定序**（分配一个执行序号）——多客户的并发写在此串行化；
5. Primary 把序号转发给 secondary，所有副本**按相同次序**执行写；
6. secondary 完成后应答 Primary；
7. Primary 应答 client（任一副本写失败则报错）。

精髓：**数据流（重的大块数据）走一条最快的路，控制流（轻的命令）走 Primary**——带宽不再经过任何单点。

### 9.5 添加（Record Append）操作流程【考点】

GFS 最重要的操作：多主机结果合并到一个文件、构造生产者-消费者队列、并发追加的语义保证。流程前半同写（问 Master → 推数据 → 发命令给 Primary），关键差异在 Primary 的检查【考点】：

- **若追加不会使该 chunk 超过最大规模（64MB）**：Primary 决定追加的 offset（当前文件末尾），在自己副本写入，并命令所有 secondary **在相同 offset** 写入；成功后 Primary 向 client 报告**写入的 offset**；
- **若会超过**：把该 chunk **填满**（padding 到 64MB，各副本一致），并通知 client **该操作要在下一个 chunk 上重试**。

由此得到的性质：client 不指定 offset，offset 由 Primary 基于当前文件大小唯一决定并返回 → 每条记录**在成功时恰好写到每个副本的相同 offset 处一次**——这就是"原子记录追加"。

### 9.6 写/追加的一致性分析：一致（consistent）与确定（defined）【考点】

**定义**（必背）：
- **一致 consistent**：所有 client 无论从哪个副本读，**看到相同的数据**；
- **确定 defined**：client 不仅看到一致数据，而且能看到**自己提交的全部更新内容**——即写入结果就是用户所写、未受并发写干扰（此时也必然一致）。

情形表【考点】（判断题高频）：

| 操作情形 | Write（常规写） | Record Append（记录追加） |
|---|---|---|
| 串行化成功 | **确定的** | **确定的**，但**穿插不一致**（interspersed with inconsistent） |
| 并发成功 | **一致但不确定** | 同左列 append 情形 |
| 失败 | **不一致** | 同左 |

逐行解释：
- **串行写成功 = defined**：client 自己知道写了哪个范围、写了什么，且多副本都成功 → 看到的就是自己写的。
- **并发写成功 = 一致但不确定**：多个 client 的写范围可能交叉覆盖，**只有 Primary 知道最终次序**，单个 client 无法知道交叉区最终是谁的内容——但所有副本按同一序号执行，所以各副本一致。这就是 **consistent but undefined**（配套 docx 的例子：M、N 两客户并发改写 A 尾部与 B 头部；A1 决定次序 M1→N1，B1 决定 N2→M2，最终 A 尾是 "77777"、B 头是 "66666"——所有客户看到的相同（一致），但不等于任何一方的完整意图（不确定））。
- **append = defined（无论串行并发）**：offset 由 Primary 指定并返回，client 能确切知道写到了哪里 → 确定；若中途某副本失败（如 50–80 区间各副本不一致），重试成功后 80–110 一致 → 整体状态是"**穿插着不一致**"（inconsistent 区间夹在 consistent 区间之间）。

配套机制【考点】：对 chunk 的所有副本按**相同顺序**执行追加；用 **chunk 版本号**检测陈旧副本（Master 维护，副本对不上即淘汰）。

### 9.7 容错、数据完整性与空间管理

- **快照**：用引用计数（copy-on-write）实现——快照时对 chunk 引用计数 +1，写时才真正复制。
- **恢复**：无论怎么终止，Master 和 chunkserver 都能在**几秒钟内**恢复状态运行；Master 的状态/操作日志/检查点在多台机器上有备份，外部监视器发现 Master 故障后改域名启动备份机，客户无感。
- **数据完整性**：每个 chunk 分成 **64KB 小块**，各配 **32bit 校验和**；读时先验证校验和再返回数据；发现错误即报告，Master 换副本重读。
- **垃圾收集**：删除文件不立即回收空间（先改名隐藏），延迟到后台垃圾收集在文件与 chunk 两级检查中回收——Master 不认识的副本即垃圾；比即时回收更简单、可靠。
- **副本放置**：新 chunk 优先放磁盘利用率低的服务器、限制单机"新建"次数、跨机架放置。

## 第 10 章 P2P、DHT 及 Chord

> 本章主线：中心服务器分发大文件撑不住 → 让接收者互助（P2P）→ 但"去哪里找资源"成了新问题 → 一致性哈希解决"节点增减时数据少搬家" → DHT 把哈希表拆给全网 → Chord 是最经典的 DHT：环拓扑 + Finger Table 把查询从 O(N) 降到 O(logN)。

### 10.1 P2P 的动机、挑战与拓扑分类

**动机（分发大文件）**：C/S 模式下服务器上行带宽有限、可服务的客户端有限；加服务器/加带宽都要真金白银的基础设施。替代方案：**让接收者互助**——每人拿到副本后顺手分发给其他人，服务器负担随下载人数增加反而被摊薄。

**P2P 的挑战**【考点】：节点频繁加入/退出（churn，随时上下线、IP 还会变）；如何定位"现在在线且有我要的内容"的节点；如何激励（为什么下载完不走？为什么上传？）；如何高效下载。

**四类拓扑**【考点】：
1. **中心化**（Napster 型）：中心索引服务器只存"谁有什么"的索引，文件本体仍在各节点——单点失效 + 性能瓶颈；
2. **分布式非结构化**：在现有网络上加一层**重叠网络 overlay**（应用层虚拟网络，虚拟节点连真实节点），节点自组织搜索——结构自由但**资源发现性能低下**（靠洪泛）；
3. **分布式结构化**：overlay 按**某种结构**组织，资源可高效定位（DHT 属此类）；
4. **半分布式/混合**：选性能好的节点当**超级节点**存其他节点信息，兼取中心化与分布式的优点。

结构化 P2P 要解决的两个核心问题：
- **路由**：节点互不相识怎么转发消息？→ 应用层路由：每节点有名字（ID）、定义互连关系、维护连接。折衷：路由表大小与消息跳数都取 **O(logN)**。遗留：高动态下维持正确结构（churn）。
- **检索**：谁有我要的资源？→ **DHT**：hash.insert(key, value)，每个节点负责哈希空间的一块、发布数据索引、按 key 检索——**用固定算法替换固定服务器**。遗留：模糊搜索、范围搜索不擅长（哈希打散了顺序）。

### 10.2 一致性哈希算法【考点】

**先看朴素方案的死穴**：`hash(key) % N` 把 key 摊到 N 台服务器。一旦扩缩容（N 变了），**几乎所有 key 的归属都变**——缓存全部失效、全系统重新搬数据。P2P 系统里节点加入退出是家常便饭，这不可接受。

**一致性哈希要满足的 4 个条件**【考点】：
1. **平衡性 Balance**：哈希结果尽量均匀分布到所有缓冲，所有缓冲空间都被利用到；
2. **单调性 Monotonicity**：已有内容已分派到某缓冲，新增缓冲后，已有内容**只能留在原缓冲或移到新缓冲**，绝不会被移到其他旧缓冲（线性哈希 x→(ax+b) mod P 就败在这——P 一变全体重排）；
3. **分散性 Spread**：不同终端可见的缓冲集合不同时，同一内容应尽量不被映射到不同缓冲（避免冗余存储）；
4. **负载 Load**：同一缓冲不被不同终端映射进不同内容（分散性的另一面）。

**算法本身**【考点】：
1. 把**每个服务节点**按其 hash 放到 **0 ~ 2³² 的圆环（continuum）**上；
2. 把**要存的 key** 用同样的哈希放到环上；
3. key 从自己的位置**顺时针**找，遇到的**第一个节点**即负责存储；转满一圈没有节点就存到第一个节点。

效果：key 归属只取决于它顺时针方向的最近节点——**增删一个节点，只影响环上相邻的一段**，平均只有 **1/N 的键需要搬家**，其余缓存全部保留（呼应单调性）。

路由：每节点存**上行节点**（ID 比自己大的最小者）与**下行节点**（ID 比自己小的最大者）；查询不属于自己范围就向上/下行转发；节点加入/退出时相邻节点更新列表。

今天的应用：分布式 Web 缓存、推理集群的 **KV Cache 亲和路由**（有状态请求必须路由到已缓存前缀的机器；取模哈希扩缩容时缓存全灭，一致性哈希只失效 1/N）。

### 10.3 分布式哈希表（DHT）的主要思想【考点】

**定义**：一种分布式存储方法——**不需要服务器**，每个客户端负责一小范围的路由、存储一小部分数据，共同实现整个 DHT 网络的寻址与存储。一致性哈希通常被视为 DHT 的一种实现。

**四步思想**（必背）：
1. 内容索引抽象为 **⟨K, V⟩ 对**：K = Hash(内容关键字)（如文件名摘要），V = 实际存储位置（节点 IP 等）；例：⟨hash("电影,夜宴"), http://video.com.cn/yeyan.avi⟩；
2. 所有 ⟨K,V⟩ 组成一张**大 Hash 表**——它保存了全网所有内容的索引；
3. 每个节点随机/按规则生成**节点 ID**（常为 IP 的哈希）；把大表**分割成许多小块**，按"**K 与节点 ID 之间的映射规则**"分给各节点维护——这个规则同时决定了节点在应用层形成**结构化重叠网络**的拓扑（CAN、Chord、Pastry、Tapestry 规则各异）；
4. 查询：给定 K，按映射规则在 overlay 上**路由**到负责节点，取出 V。

**三要素**【考点】：**定位 Locating**（K → 节点 ID 的映射关系）；**路由 Routing**（overlay 上按 ID 逐跳转发，每节点存邻近节点的 ID/IP）；**网络拓扑**（由映射规则决定；拓扑动态变化，要处理节点加入/退出/失效；节点始终以 ID 标识并按 ID 路由）。

### 10.4 Chord 原理【考点】

Chord（MIT，2001）要解决的根本问题：**P2P 网络中如何找到存有特定数据的节点**。它在一致性哈希之上补了两件事：具体化的哈希算法 + 优化的路由算法（查询跳数 O(N) → O(logN)），并对节点加入/退出做了优化。

**哈希算法**：一致性哈希未规定具体函数，Chord 规定用 **SHA-1**，生成 **m 位**的节点 ID（NID）与键 ID（KID）（例 m=6，环上有 64 个位置）。

**Hash 表分布规则**【考点】：
- 节点按 ID 从小到大排成一个**逻辑环（Chord 环）**；
- ⟨K,V⟩ 存放在 **Successor(K)**——从 K 开始**顺时针方向距离最近的节点**；
- API：Insert(K,V)、Lookup(K)、Update(K,new_V)、Join(NID)、Leave()。

**简单查询（朴素版）**：每节点只维护**后继节点**的 ID、IP；查询消息沿环一跳一跳传，直到 K 落在（某节点 ID, 其后继 ID] 区间——正确但太慢，**O(N)**。

**Finger Table（指针表）扩展查找**【考点】（本章核心计算点）：
- 节点 n 的指针表共 m 项，第 i 项 = **successor[n + 2^(i−1)]**（1 ≤ i ≤ m）——即"n 后面第 2^(i−1) 个位置的后继节点"（例 N8 的表项：N8+1→N14、N8+2→N14、N8+4→N14、N8+8→N21、N8+16→N32、N8+32→N42）。
- 查询时**每次至少把与目标的距离缩短一半**（选表中不超过目标的最大的 2 的幂跳过去）→ 指针表 O(logN) 项、查询约 **O(logN) 跳**。
- 例：N8 查 K54 → 顺指针表跳到 N42 → N42 的表跳到 N48 → 到达 Successor(54)=N56，三跳搞定。

**网络波动（Churn）的处理**【考点】：
- **节点加入**：新节点 N 通过某个已知节点**初始化自己的指针表**（请它代查各表项）；其他节点运行周期性**探测协议**后把 N 反映进相关指针表和后继指针；**N 的后继把小于 N 的所有 K 移交给 N**（数据归属随之调整）；
- **节点退出/失效**：所有指针表中包含 M 的节点，把相应指针改指 **M 的后继**（大于 M 的第一个有效节点）；为保证进行中的查询不受影响，每节点维护 **r 个最近后继的后继列表**——发现后继失效，就用列表里第一个正常节点顶替；
- 探测协议周期运行，持续检测新加入/退出/失效节点，更新指针表与后继指针。

**拓扑失配问题**【考点】：O(logN) 是**逻辑跳数**，但每一逻辑跳在物理网络上可能跨自治域、跨国家——overlay 与物理网络脱节，**实际寻路时延大**。

**总结**【考点】：算法简单；可扩展（查询通信开销与节点维护状态都随节点数 **O(logN)** 增长）；存在拓扑失配问题待解。
