### 作业 1：三个事务的串行等价交错执行（来源：DS.pdf 第 1 题）

> 题干按手写答案反推还原（原题干未入镜；事务定义由答案中的操作行推得）。

设三个事务对对象 i、j、k 执行如下操作：

```
事务 T：x = read(i);  y = read(j);  write(j, 10)
事务 U：m = read(k);  write(i, 30); n = read(i)
事务 V：p = read(k);  z = read(i);  write(j, 20)
```

**题目**：分别给出两个**串行等价**的交错执行，并写出每种情况下 i、j 的最终值。

【参考答案】（即 DS.pdf 手写内容）

**情况一：等价于 T → U → V，最终 i = 30，j = 20**

| 步骤 | 事务 | 操作 |
|---|---|---|
| 1 | T | x = read(i) |
| 2 | T | y = read(j) |
| 3 | U | m = read(k) |
| 4 | V | p = read(k) |
| 5 | T | write(j, 10) |
| 6 | U | write(i, 30) |
| 7 | U | n = read(i) |
| 8 | V | z = read(i) |
| 9 | V | write(j, 20) |

**情况二：等价于 V → U → T，最终 i = 30，j = 10**

| 步骤 | 事务 | 操作 |
|---|---|---|
| 1 | V | p = read(k) |
| 2 | U | m = read(k) |
| 3 | V | z = read(i) |
| 4 | U | write(i, 30) |
| 5 | V | write(j, 20) |
| 6 | U | n = read(i) |
| 7 | T | x = read(i) |
| 8 | T | y = read(j) |
| 9 | T | write(j, 10) |

**验证要点（串行等价充要条件）**：所有冲突操作对在两种情况下都保持一致方向——
- 对象 i：T.x 读 → U.write(30) → V.z 读（情况一）/ V.z 读 → U.write(30) → T.x 读（情况二），各事务对 i 的相对次序全程一致；
- 对象 j：T.write(j,10) 与 V.write(j,20) 的先后与所等价的串行次序一致。

### 作业 2：两阶段提交协议（2PC）的缺陷与改进（来源：DS.pdf 第 2 题）

**题目**：分析两阶段提交协议（2PC）存在哪些缺陷？说明如何避免对单一协调者最终通知的完全依赖（阻塞问题），以及如何通过日志与恢复机制提高故障修复能力。

【参考答案】（即 DS.pdf 手写内容）

1. **2PC 的缺陷**：同步阻塞、单点故障，以及可能出现的数据不一致。
2. **避免阻塞——三阶段提交协议（3PC）**：把 2PC 的第二阶段进一步拆分，在正式提交前增加一个**预提交阶段**，使参与者在协调者故障时能**根据自身状态以及其他参与者的状态**进一步判断事务结果，从而降低 2PC 的阻塞问题。
3. **日志与恢复机制提高故障修复能力**：
   - 协调者和参与者把事务状态写入**持久化日志**；
   - 参与者处于 **uncertain** 状态恢复后，通过 **getDecision** 向协调者查询最终结果；
   - 协调者恢复后**根据日志**重新发送 **doCommit** 或 **doAbort**。

（对应知识点：2PC 三缺陷、恢复动作表——见《分布式系统-知识点整理.md》第 6.4、6.7 节。）

### 作业 3：Lamport 逻辑时钟计算（来源：IMG20260909210854.jpg）

**题目**：三个进程 A、B、C 通过消息传递交互（时空图中标出事件 a–g 及消息箭头；各进程逻辑时钟初值为 0）。按 Lamport 规则（LC1：执行事件前 L:=L+1；LC2：发送附时间戳 t，接收方 L:=max(L,t) 再 +1）计算事件 a–g 的逻辑时钟。

**手写答案**（照片辨识，个别字母不清）：

```
L(a) = 1    L(b) = 2    L(d) = 2    L(e) = 3*    L(f) = 4    L(g) = 5    L(c) = 6
```

\* 照片中该处字母似写作 "g"，但 g 已取 5；按 a–g 七个事件各取一值推断此位应为 **e = 3**。

**解题要点**：d 与 b 同值（=2）是判断题高频陷阱——接收方取 max 后 +1，不同链路可得到相同时间戳；`L(a)<L(b)` 推不出 `a→b`（Lamport 时钟无反向因果）。

### 第 4 章

**思考题 4.1（课件 p88，Paxos）**：容忍 f 个 acceptor 故障，需要多少个 acceptor？
【参考答案】：**2f + 1**（多数派 quorum，任意两个多数派相交）。

**思考题 4.2（课件 p111，PBFT）**：
1. 为什么客户端只等 **f+1** 个 reply，而 prepare/commit 阶段要 2f+1？
2. 如果 primary 失效怎么办？

【参考要点】：prepare/commit 需 2f+1 是为了两个 quorum 交集必含一个**正确**副本，保证提案安全；执行阶段安全性已由前两阶段保证，f+1 个回复中必有至少 f+1−f = 1 个来自正确副本即可安全返回。primary 失效 → **view change**：超时触发，新主为 `p = v mod |R|`（v 为视图编号）。

**参考题 4.3（课件 p93）**：附 CMU 分布式系统期末考试拜占庭相关真题（图示题，课件仅给出截图，可作练习素材）。

### 第 5 章

**讨论题 5.1（课件 p88–89）**：给出事务 T、U：

```
T：write(i,10);  y = read(j);  x = read(i);  write(j,20)
U：m = read(k);  write(i,30);  n = read(j);  write(k,40)
```

课件展示的一个交错（U 先做 m=read(k)，随后 T 的 write(i,10)…U 的 write(i,30)…T 的 x=read(i)…）——**判断其是否串行等价**。
【参考答案】：**非串行等价**（T 对 i 的读在 U 写后、T 对 j 的写在 U 的 n=read(j) 之后，冲突对方向不一致：对象 i 上 T→U，对象 j 上 U→T）。

**讨论题 5.2（课件 p90–91）**：给出事务 T、U：

```
T：x = read(j);  y = read(i);  write(j,10);  write(i,20)
U：m = read(k);  write(i,30);  n = read(j);  write(k,40)
```

给出串行等价的交错执行。
【参考答案】：课件给出两个方向均可行——先 T 后 U（T 的 x、y 读都在 U 写之前）或先 U 后 T（U 全部操作先执行）；关键是用充要条件逐一核对每对冲突操作的次序一致。

**讨论题 5.3（课件 p92，加锁）**：下列加锁方式是否正确？

```
T：给 i 加锁 → x=read(i) → 释放 i 的锁 ……（后续）给 j 加锁 → y=read(j) → commit 释放 j 的锁
U：给 i 加锁 → write(i,1) → 给 j 加锁 → write(j,2) → commit 释放 i、j 的锁
```

【参考答案】：**错误加锁方式**——T 读完 i 立即释放 i 的锁，违反了**两阶段锁协议**（释放任一锁后不得再申请新锁），两事务的冲突操作次序无法保证一致。

**讨论题 5.4（课件 p93–97，乐观并发控制·向后验证）**：设 U 先提交成功；T 随后验证：

```
T：openTransaction; x=read(i); …… y=read(m); write(n,3); closeTransaction  → 验证失败，放弃
U：openTransaction; write(m,1); write(n,2); commit → 验证成功，提交
```

1. 原向后验证算法（比较 T 的**整个读集**与 U 的**写集**）判定 T 验证失败——该结果满足串行等价吗？
2. 算法有无改进余地？

【参考答案】：
1. **满足串行等价**（T 放弃无效果，等价于先 U 后 T）。
2. **有改进余地**：T 读 m 发生在 U 提交**之后**，不可能读到 U 写前的旧值，不应判冲突。改进算法：只比较 **T 在 U 提交之前已读的成员**组成的集合与 U 的写集——此处为 {i}，与 U 的写集 {m,n} 交集为空 → 验证**成功**，T 可提交（等价于先 T 后 U），提高了并发度。

## 三、相关文件分析题

### 分析题 A：GFS 并发写"一致但不确定"（来源：GFS-并发写成功-consistent but undefined.docx）

**题目**：文件 F 包含 2 个 chunk：A、B（B 为 63MB，未填满）。A、B 的 3 个副本分别为 A1/A2/A3、B1/B2/B3。A 的最后 5 个字节与 B 的前 5 个字节均为 "55555"。两个客户 M、N 同时发起改写，且改写内容均为 A 的最后 5 字节和 B 的前 5 字节：M 改为 10 个 "6"，N 改为 10 个 "7"。GFS 将每个客户的请求拆成 2 个（M1/M2、N1/N2），涉及两个不同的主副本管理器（A1、B1），已知 A1 确定的写顺序为 M1、N1；B1 确定的写顺序为 N2、M2。分析写完成后 A、B 各副本的状态，并说明结果"一致"与"确定"与否。

【参考答案】（即 docx 内容）：
- 写完后 **A 的 3 个副本最后 5 字节为 "77777"**（A1 主导：先 M1 后 N1），**B 的 3 个副本前 5 字节为 "66666"**（B1 主导：先 N2 后 M2）。
- **结论：一致（所有客户看到相同结果），但不确定（两个用户的改写交错执行，最终内容不等于任一客户完整所写的内容）**。
- 要点：同一 chunk 内 Primary 决定唯一写序 → 副本间一致；但并发写的交叉区由 Primary 定序决定，客户端无法预知 → "consistent but undefined"。这正是 GFS 放松一致性模型、以 Record Append 提供确定追加语义的动机。

### 分析题 B：Gossip 系统状态推演（来源：Gossip讲义.docx）

**题目**：3 个副本管理器 rm0/rm1/rm2 及对应前端 fe0/fe1/fe2，操作序列如下：
① fe0 更新 x=1（rm0 处理并 gossip）→ ② fe1 查询 x=?、更新 x=2（rm1 处理并 gossip，其中发给 rm2 的 gossip **丢失**）→ ③ fe0 查询 x=?、更新 x=3（rm0 处理并 gossip）。
要求：写出每一步各 RM 的 val、val.ts、replica.ts、log、executed 的变化；验证因果次序执行（rm2 推迟 x=3 直至 x=2 稳定）；验证日志删除条件；并分析 fe0 连到 rm2 时查询是否会阻塞。

【参考要点】（详见讲义全文，逐步推演）：
- 更新流程：`replica.ts[i] += 1`；`ts = u.prev` 且 `ts[i] = replica.ts[i]`；日志记 `<i, ts, u.op, u.prev, u.id>`；返回 ts 给 FE merge。
- gossip 接收：若发送方 replica.ts ≤ 本地 replica.ts 则丢弃；否则合并时间戳与日志，执行所有"未执行且满足稳定性条件 u.prev ≤ val.ts"的更新。
- **因果推迟实例**：rm2 收到含 x=3（prev=(1,1,0)）与 x=2（prev=(1,0,0)）的日志时，因 val.ts=(1,0,0) 不满足 x=3 的稳定条件 → 先执行 x=2（val=2, val.ts=(1,1,0)）→ 再满足 x=3（val=3, val.ts=(2,1,0)）。
- **日志删除验证**：记录 r 可由创建者删除 ⟺ 所有 RM 的 tableTS[i][c] ≥ r.ts[c]（讲义对 fe0_1、fe0_3、fe1_2 逐一验证，并给出"中间时刻 fe1_2 尚不可删"的反例）。
- **查询阻塞验证**：fe0 在 x=3 更新后、第二个 gossip 到达 rm2 前连到 rm2 查询：q.pre=(2,1,0) > rm2.val.ts=(1,0,0) → 不满足回答条件，**阻塞**（保留队列等待）。
